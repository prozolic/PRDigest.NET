### [#136019](https://github.com/dotnet/runtime/pull/136019) Report byref-like struct arguments to the GC in helper-based tail calls {#136019}
- 作成者: [@EgorBo](https://github.com/EgorBo)
- 作成日時: 2026年10月18日 02:26:19(UTC)
- マージ日時: 2026年10月18日 18:47:30(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-VM-coreclr/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-VM-coreclr</span></a>
#### 概要
ヘルパーベースの末尾呼び出し（tail call）で、`Span<T>` のような byref-like 構造体の引数が GC に報告されない問題を修正します。

`TailCallHelp::GenerateGCDescriptor` は GC シリーズを持たない値型をスキップしていましたが、`Span<T>` などの byref-like 構造体は GC シリーズを持たないものの内部ポインタ（interior pointer）を含みます。そのため、tail call の引数バッファに格納されている間は GC に報告されず、`IL_STUB_StoreTailCallArgs` と `IL_STUB_CallTailCallTarget` の間で GC が発生すると、呼び出し先が配列の旧位置を指す古いポインタを受け取る可能性がありました。

修正では、GC ディスクリプタ構築時に byref-like 構造体を GC ポインタを持つ構造体と同様に扱います。`getClassGClayoutStatic` はすでに byref フィールドを `TYPE_GC_BYREF` として報告するため、それを利用できます。

#### 変更内容
- `src/coreclr/vm/tailcallhelp.cpp`（+2/-1）: `GenerateGCDescriptor` で byref-like 構造体を GC ポインタを持つ構造体と同様に扱うよう条件を変更
- `src/tests/JIT/Regression_2/Runtime_136010/Runtime_136010.il`（+117/-0）: `Span<int>` 引数を持つヘルパーベースの tail call を行う最小限の IL 回帰テストを追加
- `src/tests/JIT/Regression_2/Runtime_136010/Runtime_136010.ilproj`（+9/-0）: 上記テスト用のプロジェクトファイルを追加

#### パフォーマンスへの影響
影響なし（提供された情報にベンチマーク結果の記載はありません）

#### 関連Issue

### [#136013](https://github.com/dotnet/runtime/pull/136013) Use memory.copy for the memmove QCall on browser-wasm {#136013}
- 作成者: [@lewing](https://github.com/lewing)
- 作成日時: 2026年10月17日 23:54:51(UTC)
- マージ日時: 2026年10月18日 23:46:35(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/arch-wasm/index.html"><span style="background-color: #eb6420; color: #ffffff; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">arch-wasm</span></a> <a style="text-decoration:none;" href="../../labels/area-VM-coreclr/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-VM-coreclr</span></a> <a style="text-decoration:none;" href="../../labels/os-browser/index.html"><span style="background-color: #FEF2C0; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">os-browser</span></a>
#### 概要
browser-wasm 向け CoreCLR で、`memmove` の QCall を emscripten libc (musl) の `memmove` 直結から、`__builtin_memmove` を呼ぶ小さなラッパーに切り替える変更です。

- 従来の emscripten libc (6.0.2) の `memmove` は、非オーバーラップ時は `memcpy`（n >= 512 で `memory.copy`）に転送しますが、オーバーラップ時は `-mbulk-memory` の有無にかかわらず常にスカラーループで処理していました。
- `SpanHelpers.Memmove` はオーバーラップするバッファを `memmove` QCall に渡すため、CoreCLR wasm 上の `Span<T>.CopyTo` / `Array.Copy` のオーバーラップ時が Mono インタープリター（jiterpreter が `memory.copy` を出力）より大幅に遅くなっていました（Mono interpreter と CoreCLR composite R2R の比較で `Span<Char>.CopyToOverlap(Size: 3000)` が約20倍、`Span<Byte>.CopyToOverlap(Size: 3000)` が約13.6倍遅い）。
- `__builtin_memmove` は `-mbulk-memory` 有効時に `memory.copy` へ lowering されます。
- ブラウザ専用の変更で、wasi-sdk 34.0 は `memmove` に既に `memory.copy` のパスがあるため影響を受けません。

#### 変更内容
- `src/coreclr/vm/qcallentrypoints.cpp`（+21/-0）: browser 向けの `memmove` QCall を `__builtin_memmove` を呼ぶラッパーにバインドするよう変更。emsdk に emscripten-core/emscripten#27654（`__builtin_wasm_memory_copy` による memmove、emscripten 6.0.10+）が入ったらラッパーを削除する旨の TODO を記載。
- `src/libraries/System.Private.CoreLib/src/System/SpanHelpers.ByteMemOps.cs`（+2/-0）: 変更行数は +2 のみで、内容は提供情報からは不明です。

#### パフォーマンスへの影響
composite R2R の browser-wasm publish（`PublishReadyToRun=true`）、Release、node 上で、オーバーラップするバイト `CopyTo`（dest = src + 1）を計測した結果（1呼び出しあたり ns）:

| Size | Before | After |
|---|---|---|
| 1024 | 292 | 29 |
| 3000 | 782 | 44 |
| 6000 | 1520 | 74 |
| 12000 | 3030 | 136 |

- 非オーバーラップの対照ケースは変化なし（3000で約43ns、6000で約125ns）。
- ベンチマークは dotnet/performance の `Span<T>.CopyToOverlap` 形式です。
- 計測は arm64 macOS 1台のみで、同一マシン上で Mono は計測していません。

#### 関連Issue
[#136012](https://github.com/dotnet/runtime/issues/136012)（emsdk のバンプを追跡）

#### その他
- 検証内容: browser-wasm Release で `clr.native` と `clr+libs+packs` をビルドし、オブジェクトに `memory.copy` が含まれることを確認。上記の R2R publish ベンチマークも実行。

#### 概要
HTTP/1.1のチャンク形式リクエストおよびHTTP/2のDATAフレームのボディ受信バッファを、チャンク／フレームごとに正確なサイズで再確保する方式から、容量を幾何級数的に拡大する方式へ変更しています。従来は固定サイズの断片を受信するたびに蓄積済みボディ全体をコピーしていたため、2次関数的なコピーコストが発生していました。この変更により、ループバックサーバーで大きなペイロードを扱う一部のテストが、作成者の環境で「数分から数秒」に短縮されたとのことです。

#### 変更内容
- `src/libraries/Common/tests/System/Net/Http/GenericLoopbackServer.cs` (+13/-0): バッファ拡張用の共通処理が追加されています（詳細な実装内容は提供情報からは不明）。
- `src/libraries/Common/tests/System/Net/Http/Http2LoopbackConnection.cs` (+9/-6): HTTP/2のDATAフレームのボディバッファを幾何的に拡張する方式に変更しています。
- `src/libraries/Common/tests/System/Net/Http/LoopbackServer.cs` (+9/-6): HTTP/1.1のチャンク形式リクエストのボディバッファを幾何的に拡張する方式に変更しています。

主な技術的ポイント:
- 使用済み長と容量を別々に管理します。
- 容量が不足する場合は倍増させ、より大きな断片が来た場合は必要サイズまで直接拡張します。
- 戻り値を返す直前に1回だけトリミングします。
- 返却されるボディの長さ、および null と空の扱いは従来どおり維持されます。
- 投機的な容量は配列長の上限で頭打ちにし、必要長の計算にはcheckedな算術を使用します。

なお、変更対象はすべてテスト用ヘルパー（`Common/tests`配下）であり、公開APIやランタイム／ライブラリ本体の実装への影響はありません。

#### パフォーマンスへの影響
- テスト用ループバックサーバーの処理が対象です。ボディ蓄積時のコピーが2次関数的から償却線形へ改善され、大きなペイロードを使うテストが作成者のマシンで数分から数秒に短縮されたと報告されています。

- ランタイム本体の性能への影響はありません。

### [#135943](https://github.com/dotnet/runtime/pull/135943) \[NativeAOT\] Hash relocations in method body folding keys {#135943}
- 作成者: [@andrew-kulikov](https://github.com/andrew-kulikov)
- 作成日時: 2026年10月16日 11:23:35(UTC)
- マージ日時: 2026年10月18日 01:43:35(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/community-contribution/index.html"><span style="background-color: #c2e0c6; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">community-contribution</span></a> <a style="text-decoration:none;" href="../../labels/area-NativeAOT-coreclr/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-NativeAOT-coreclr</span></a>
#### 概要
NativeAOT (ILCompiler) のメソッド本体フォールディング（重複排除）において、`MethodInternKey` のハッシュにリロケーション（再配置情報）を含めるよう変更しました。従来はコードバイト・GC情報・フレーム情報・EHバイトのみをハッシュしていたため、リロケーション先だけが異なるメソッド本体が同一ハッシュ値となり、同じ `HashSet` バケットに集中して `AreSame` の比較が O(n²) になっていました。特に最適化済みコードでは、async メソッドごとに生成されるステートマシン構造体のため、`AsyncStateMachineBox<TResult, TSM>.MoveNext` や `AsyncMethodBuilderCore.Start<TSM>` などがバイト列同一のコピーとして大量に発生し、この問題が顕著になります。

#### 変更内容
- `src/coreclr/tools/aot/ILCompiler.Compiler/Compiler/MethodBodyDeduplicator.cs` (+29/-2)
  - ハッシュ計算にリロケーション情報を追加し、`MethodInternComparer.AreSame` の比較ロジックと整合させています。
    - **リロケーション種別とオフセット:** `AreSame` で厳密比較されるため、そのままハッシュに含めます。
    - **`MethodReadOnlyDataNode` のターゲット:** `AreSame` が内容比較するため、データバイトをハッシュに含めます（比較対象の部分集合）。
    - **その他のターゲット:** 前回パスのリマッピングを通した後のターゲットの同一性（identity）をハッシュします。`AreSame` は `remapping[t1] == t2`（またはその逆）を等価とみなしますが、リマッピングの値はキーにならない（キーになるのは既存の本体と一致した本体のみで、セット内の本体はキーにならない）ため、双方とも `id(t2)` をハッシュします。
  - `Equals` が受理するペアの集合は不変で、バケット分布のみが変わります。反復順序は従来どおりソート済みの `GetCompiledMethodBodies()` で、`ISymbolNode` はすでに identity でハッシュされます。そのため出力は変わりません。

#### パフォーマンスへの影響
コンパイル時間（ILC実行時間）が大幅に改善されます（v10.0.13 に同変更を適用、osx-arm64 ホスト・M1 Pro での計測）。

| | 変更前 | 変更後 |
|---|---:|---:|
| iOSアプリ（約12,000 async メソッド）ILC実行時間 | 約1200秒 | 247〜252秒 |
| 同、`--methodbodyfolding:none` | 252秒 | |
| 8000個の `async Task<int>` メソッドのサンプル `dotnet publish` | 271秒 | 16秒 |
| 同サンプル、4000メソッド | 47秒 | 9秒 |

- すべてのケースで、生成されるオブジェクトファイルは未修正コンパイラと**バイト単位で同一**でした（iOSアプリの 1.19 GB の `.o`（2回実行）およびサンプルの `.o`）。
- `__managedcode` はフォールディングによるサイズ削減効果を維持しています（フォールディングなし 80.0 MB に対し 69.3 MB）。
