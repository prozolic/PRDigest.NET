### [#136734](https://github.com/dotnet/runtime/pull/136734) JIT: Mark memset/memcpy and monitor helpers as heap-mutating {#136734}
- 作成者: [@EgorBo](https://github.com/EgorBo)
- 作成日時: 2026年10月30日 20:29:23(UTC)
- マージ日時: 2026年10月30日 23:45:26(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-CodeGen-coreclr/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-CodeGen-coreclr</span></a>
#### 概要
JITの `HelperCallProperties` において、`CORINFO_HELP_MEMCPY`、`MEMZERO`、`MEMSET`、`NATIVE_MEMSET` はメモリへ書き込むにもかかわらず、ヒープを変更するヘルパーとして扱われていませんでした。そのため Value Numbering、メモリ liveness、ループの副作用解析がこれらの呼び出しをメモリに対する no-op とみなし、周辺のロードが誤って CSE されたりループ外へホイストされたりする問題がありました。本PRはこれらのヘルパーをヒープ変更ありとしてマークします。あわせて `MON_ENTER`/`MON_EXIT` も同様に扱います（フルメモリバリアであり、`*lockTaken` にも書き込むため）。

問題となるコード例（PR説明より）:

```csharp
int a = *p;
Unsafe.InitBlockUnaligned(p, 0, n); // non-constant size -> CORINFO_HELP_MEMSET call
return a + *p;                      // *p gets the same VN as 'a', CSE returns 2*a instead of a

for (...)
{
    sum += *p;                          // hoisted out of the loop
    Unsafe.InitBlockUnaligned(p, 0, n);
}
```

#### 変更内容
- `src/coreclr/jit/utils.cpp`（+9/-3）
  - `CORINFO_HELP_MEMCPY`、`MEMZERO`、`MEMSET`、`NATIVE_MEMSET` を heap-mutating としてマーク
  - `CORINFO_HELP_MON_ENTER`/`MON_EXIT` も heap-mutating としてマーク

#### パフォーマンスへの影響
主目的は正確性の修正です。これらのヘルパー呼び出しをまたぐロードの CSE やループ外へのホイストが行われなくなるため、該当箇所では最適化の機会が減る可能性があります。ベンチマーク結果は提供されていませんが、PRにはJITのdiffへのリンクが記載されています。

#### 関連Issue
なし

#### その他
- 影響範囲はCoreCLRのJIT内部実装（公開APIの変更ではありません）。
- 修正前は、メモリ書き込みヘルパー呼び出しをまたいだ読み取りが同じ値番号を持ち、誤った結果（例: `2*a`）を返し得ました。修正後はこれが防がれます。

### [#136667](https://github.com/dotnet/runtime/pull/136667) Fix GC-time type loads in ReadyToRun transition frames after #135805 {#136667}
- 作成者: [@lewing](https://github.com/lewing)

#### 概要
#135805 以降、ReadyToRun のトランジションフレームで GC 時に型ロードが走り、`!IsGCThread() && !IsStackWalkerThread()` アサート（clsload.cpp:3001）が発生する問題の修正です（VMR のシナリオテストで再現）。同種の問題がもう1箇所見つかったため、合わせて修正しています。

#135805 で呼び出し側の `TYPE_HANDLE` フィクスアップが削除され、import の GCRefMap を持つターゲットはシグネチャ型のロードをスキップできるようになりました。しかし GC 時の2つのパスはその型を依然として必要としていました。

1. **フィクスアップフレームのジェネリックコンテキスト（VMR クラッシュ）**
   - `ExternalMethodFixupWorker` が `ExternalMethodFrame` を積んだままターゲットの prestub を実行します。
   - そこで GC が走ると `TransitionFrame::GetParamTypeArg` → `ArgIterator` が戻り値型を必要とし、未ロードの `Span<__Canon>`（System.Linq の `Enumerable.Any<__Canon>` → `CollectionsMarshal.AsSpan<__Canon>`）の型ロードが GC スレッド上で発生していました。
   - フレームが GCRefMap を持つ場合、`GetParamTypeArg` はマップの `METHOD_PARAM`/`TYPE_PARAM` トークンから引数位置を読むようになりました（`ExternalMethodFrame` の import map、および prestub / call-counting フレームの exact-entry map が対象）。
   - `StubDispatchFrame` は、dispatch map が instantiation 引数を含まず、マップ参照がレシーバを読む可能性があるため対象外です。マップが無い場合は従来の `ArgIterator` パスのままです。

2. **共有コード向けジェネリック仮想メソッドの解決**
   - 共有ジェネリック R2R コードは `ResolveVirtualFunctionPointer` 経由でジェネリック仮想メソッドを解決しますが、ターゲットのインスタンス化を prepare していませんでした。
   - その結果、ターゲットの prestub 中の GC が `PromoteCallerStack` でシグネチャを辿ってローダーに到達していました。
   - 解決したターゲットを、エントリポイントを公開する前に prepare するようにしました（`RuntimeMethodHandle_GetVirtualFunctionPointer` と同様）。

#### 変更内容
- `src/coreclr/vm/frames.cpp`（+26/-0）: `GetParamTypeArg` で GCRefMap から引数位置を取得する処理を追加。
- `src/coreclr/vm/jithelpers.cpp`（+7/-10）: `ResolveVirtualFunctionPointer` で解決したターゲットを prepare してからエントリポイントを公開するよう変更。
- `src/tests/readytorun/tests/coldsignaturedispatch.cs`（+46/-0）: 各修正に対応するテストケースを追加。
- `src/tests/readytorun/tests/signaturedependency.cs`（+5/-0）: 関連するテスト調整。

#### 概要
WASI 上で `HttpClientHandler` が使用する `WasiHttpHandler`（`wasi:http` ハンドラ）の、リクエスト失敗時のハング・誤った例外・プロセス異常終了などの不具合を修正する PR です。

- **リクエスト本文の失敗でタイムアウトまでハングする問題**: `SendContent` が fire-and-forget で開始されていたため、本文のシリアライズが例外・キャンセルになっても誰も観測せず、`HttpClient.Timeout`（100秒）まで待機していました。レスポンスのポーリング中に送信タスクを監視し、本文側の例外でリクエストを失敗させるようにしました。
- **Dispose が本来の例外を隠す問題**: `Stream.Dispose()` が `WasiOutputStream.Close()` オーバーライドを呼び、送信ボディを *finish* していました。本文の失敗後に `OutgoingBody.Finish` が `WitException` を投げ、元の例外を置き換えていました。ボディの完了を明示的な `Finish()` に分離し、未完了ストリームの Dispose ではボディを abort します。
- **pollable 破棄時のトラップ**: 読み書きの pollable（子リソース）が登録されたままリクエスト/レスポンスのストリームを破棄すると、wasmtime が `resource has children` でトラップしプロセスが終了していました。ストリームを drop する前に保留中の待機をキャンセルするようにしました。
- **Chunked / Content-Length**: `wasi:http` は `Transfer-Encoding` ヘッダーを禁止しているため、`TransferEncodingChunked = true` はヘッダー検証で失敗していました。ヘッダー（および `Content-Length`）を省略してホストにチャンク化を任せ、本文なしの chunked 指定は SocketsHttpHandler と同様に `InvalidOperationException` を投げます。長さが既知のコンテンツでは `Content-Length` を計算して送信します。
- **例外型を SocketsHttpHandler に合わせる**:
  - null または相対のリクエスト URI は `InvalidOperationException`、http(s) 以外のスキームは `NotSupportedException`（従来はいずれも `ArgumentException`）
  - レスポンス本文の読み取り中の `wasi:io` ストリームエラーは、生の `WitException` ではなく `HttpIOException(HttpRequestError.ResponseEnded)`
  - レスポンスストリーム破棄後の `CanRead` は `false`

#### 変更内容
- `WasiHttpHandler.cs` (+42/-10): 送信タスクの監視、`Content-Length` / chunked の処理、URI・スキーム検証と例外型の変更
- `WasiHttpInterop.cs` (+37/-0): 追加の相互運用処理
- `WasiInputStream.cs` (+23/-4): 破棄前の pollable キャンセル、`HttpIOException` への変換、破棄後の `CanRead = false`
- `WasiOutputStream.cs` (+28/-9): 明示的な `Finish()` の導入、未完了ストリーム破棄時の abort、破棄前の pollable キャンセル

#### パフォーマンスへの影響
影響なし（性能目的の変更ではなく、ベンチマーク結果の記載もありません）。ただし、本文失敗時に 100 秒のタイムアウトを待たずに即座に失敗するようになります。

- pass から fail に退行したテストはなし
- `SendAsync_SendSameRequestMultipleTimesDirectlyOnHandler_Success`（2 ケース）は `Content-Length` 送信により pass に
- 残る OuterLoop の失敗は WASI 上の既存の問題（MD5 非対応、dev-cert のエコーサーバーへの TLS 失敗、ハンドラの未サポート機能）

### [#132788](https://github.com/dotnet/runtime/pull/132788) \[browser\]\[CoreCLR\] Enable EventPipe CPU sampling for RyuJIT/R2R on WebAssembly {#132788}
- 作成者: [@pavelsavara](https://github.com/pavelsavara)
- 作成日時: 2026年08月26日 15:23:36(UTC)
- マージ日時: 2026年10月30日 08:56:41(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/arch-wasm/index.html"><span style="background-color: #eb6420; color: #ffffff; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">arch-wasm</span></a> <a style="text-decoration:none;" href="../../labels/area-Diagnostics-coreclr/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-Diagnostics-coreclr</span></a>
#### 概要
単一スレッドのWebAssembly（browser/CoreCLR）において、RyuJITが生成するReadyToRunコード向けに、EventPipeの協調的CPUサンプリングを有効化するPRです。専用のサンプリングスレッドがないため、インストルメント済みコードが自らサンプリングを呼び出します。これはインタープリタの `INTOP_PROF_SAMPLEPOINT` に相当するR2R版です。`WasmPerformanceInstrumentation` によるプロファイリングは**publish済みアプリのみ**対応で、dev-loopビルド（ランタイムパック由来の未インストルメントなフレームワークR2Rイメージを使用）は、`PublishReadyToRun` の有無にかかわらず明確な診断メッセージで拒否されます。

#### 変更内容
- **JIT/ヘルパー追加**: `CORINFO_HELP_WASM_PROF_SAMPLEPOINT` とR2Rヘルパーを追加し、R2Rフォーマットを32.1に更新（`corinfo.h`、`jithelpers.h`、`readytorun.h`、`readytorunhelpers.h`、`jiteeversionguid.h`、`ModuleHeaders` 等）。
- **JIT（`fgwasm.cpp` 等）**:
  - インストルメントフィルタで選ばれたメソッド入口とループのバックエッジ先に、NoGCヘルパー呼び出しを挿入。
  - EH継続フローを明示化した後にWasmのDFS／後続走査を再利用し、実行不可能なモデル上の2パスEHサイクルをループとして扱わないようにした。
  - catch引数のセットアップをサンプル挿入より前に維持し、reverse P/Invoke入口のサンプルは協調モード遷移の後に配置。
  - Wasmの参照追跡で全呼び出しのオペランドを消費し、未解決参照のスピルはGCセーフポイントでのみ実施。
- **VM（`wasm/helpers.cpp`、`ep-rt-coreclr-wasm-sampling.cpp`、`ceeload.cpp`）**:
  - 標準の `HCIMPL0` ヘルパーラッパーを使用し、呼び出し元のシャドウスタックポインタから導出した `InlinedCallFrame` でスタックウォークを固定。セッション有効性と適応スキップを先にチェックしてからフレームを構築するため、無効／スキップ時はフレーム構築のコストを避けられる。
  - インタープリタとR2Rでサンプリング判定とカウンタを共有し、スタック収集は判定から分離（インタープリタの既存エントリポイントはラッパーとして維持）。
  - R2R情報のインストール時にWasm仮想IP範囲を登録し、アセンブリのアクティベーション前でもスタックウォーク可能にした。
- **SDK/ビルド（`Microsoft.NET.Sdk.WebAssembly.Pack` 配下のtargets/props、`BrowserWasmApp.CoreCLR.targets`）**:
  - フレームワークアセンブリを含むpublishクロージャ全体を、選択フィルタに従ってインストルメント。`all` はcrossgen2のMethodSetワイルドカード `*` にマップ。
  - 共通のインストルメントフックはパッケージ版／インビルド版crossgen2の両方でインポートするが、カスタムコンパイラリゾルバはインビルド構成に限定（ワークロード利用者はSDKリゾルバを維持）。
- **設定の破壊的変更**: `WasmPerformanceInstrumentation` から `interval=...` サフィックスを削除。サンプリングレートは `DOTNET_EventPipeThreadSamplingRate` を指す `WasmEnvironmentVariable` アイテムで別途設定する。Monoのbrowser/devtoolsプロファイラ記述子は変更なし。
- **テスト専用の内部モード**: 決定論的な協調サンプリングテスト用に、全サンプルポイントでサンプリングする内部モードを追加（ゼロ既定値やスレッド版の挙動は不変）。
- **テスト**: `EventPipeDiagnosticsTests` を拡張し、publishしたアプリのトレースを取得して、Debug/Releaseでサンプルされたアプリフレームを検証。既存のCoreCLR R2Rケースに以下を追加（デフォルトで実行）。
  - 参照を含む構造体のヒープコピー（NoGCバルクコピーのオペランド追跡）
  - 入れ子のfinally/filter実行（EH制御フロー、ハンドラ入口の順序）
  - アンマネージドコールバック（reverse P/Invoke入口フレームのアサーション）

  あわせて、dev-loopでの診断メッセージ確認テスト（`PublishReadyToRun` 有効／無効）を追加し、dev-loopでの成功を期待していた古いnative-defaultsのtheory行を削除。
