- 作成者: [@thomhurst](https://github.com/thomhurst)
- 作成日時: 2026年10月12日 15:10:49(UTC)
- マージ日時: 2026年10月13日 12:24:17(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-System.Diagnostics.Process/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-System.Diagnostics.Process</span></a> <a style="text-decoration:none;" href="../../labels/community-contribution/index.html"><span style="background-color: #c2e0c6; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">community-contribution</span></a>
#### 概要
Unix 上の `Process.Kill(entireProcessTree: true)` が、macOS で意図しないプロセス（GitHub ホステッドランナーの `Runner.Listener` / `Runner.Worker` 等）に `SIGHUP`/`SIGCONT`/`SIGTERM` を発生させる問題（#131944）の修正です。

従来は、ツリー全体に `SIGSTOP` を送った後、深さ優先の先行順（親が先）で `SIGKILL` を送っていました。親が先に死ぬと、停止中の子が launchd に reparent されます。その子が終了する際、XNU の `fixjobc()` が `pg_jobc` をデクリメントしてプロセスグループが誤って orphaned と判定され、`orphanpg()` が停止中のメンバーを検出して同一プロセスグループ全体に `SIGHUP` と `SIGCONT` を送っていました。

修正では、収集済みのリストを逆順に走査し、子孫を祖先より先に `SIGKILL` します。`SIGKILL` は停止状態を即座に解除するため、祖先が終了して子が reparent される時点で停止中のプロセスが残りません。

#### 変更内容
- `src/libraries/System.Diagnostics.Process/src/System/Diagnostics/Process.Unix.cs`（+9/-1）
  - 停止済みプロセスへの kill を逆順（子孫 → 祖先）に変更
  - macOS のプロセスグループに関する理由をコメントで記載

ツリー全体は kill 前にすべて収集されるため、`KillOnParentExit`（`PR_SET_PDEATHSIG`）のために導入された「停止→kill」の 2 段階方式の意図も損なわれません。

#### パフォーマンスへの影響
影響なし（記載なし）。

その他、actions/runner-images#14833 に関連する調査結果が参照されています。

### [#131826](https://github.com/dotnet/runtime/pull/131826)  \[APX\] Add Jmpabs support. {#131826}
- 作成者: [@DeepakRajendrakumaran](https://github.com/DeepakRajendrakumaran)
- 作成日時: 2026年08月04日 18:27:42(UTC)
- マージ日時: 2026年10月13日 21:50:28(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-CodeGen-coreclr/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-CodeGen-coreclr</span></a> <a style="text-decoration:none;" href="../../labels/community-contribution/index.html"><span style="background-color: #c2e0c6; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">community-contribution</span></a> <a style="text-decoration:none;" href="../../labels/apx/index.html"><span style="background-color: #eb6420; color: #ffffff; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">apx</span></a>
#### 概要
AMD64上のvirtual call stubに、Intel APX（Advanced Performance Extensions）の`JMPABS`命令（`D5 00 A1` + 8バイトアドレス）のサポートを追加するPRです。従来の `mov rax, imm64; jmp rax` による64ビット絶対ジャンプを `JMPABS` に置き換え、スタブサイズ縮小と命令フェッチ効率の改善を狙っています。
実行時に `IsJmpAbsAvailable()`（`InstructionSet_APX` の有無）で判定し、APX非対応環境では従来のエンコードにフォールバックします。
なお、当初含まれていたJITエミッタ側の変更は、レビューフィードバックにより取り下げられています。

#### 変更内容
- `src/coreclr/vm/amd64/cgenamd64.cpp` / `cgencpu.h`
  - 生の `JMPABS` 命令（11バイト）を出力する `emitJmpAbsJump()` を追加
  - `emitBackToBackJump()` を、利用可能なら `JMPABS`、不可なら従来エンコードを使うように変更（どちらも12バイト。APX側は `jmpabs`＋`nop` で揃える）
  - `IsJmpAbsAvailable()` による実行時のCPU機能検出を追加
  - 不要になった `EncodeLoadAndJumpThunk()` を削除
- `src/coreclr/vm/amd64/virtualcallstubcpu.hpp`
  - `DispatchStubShort` にAPXエンコード経路（`jne rel32; nop; jmpabs imm64`、従来と同じ18バイト）を追加
  - `DispatchStubLong` にもAPX対応のレイアウトが入り、サイズが40→48バイトに増加
  - `DispatchStubShort_offsetof_failDisplBase` マクロが誤った構造体型（`DispatchStubLong`）を参照していた問題を修正
- `src/coreclr/inc/dacvars.h`、`ceemain.cpp`、`codeman.cpp`、`SOSDacImpl.cs`
  - 関連する小規模な調整（DAC変数、初期化、cDAC側）

#### パフォーマンスへの影響
- 狙いは `mov rax, imm64; jmp rax` の2命令を単一命令にすることによる、命令フェッチ効率の改善です。
- 作成者はNOPパディングで従来とスタブサイズを揃えているため、short系スタブでのサイズ縮小は実際には発生していません。
- ベンチマーク結果などの具体的な数値はPR内に示されていません。レビューでも、APX/従来の両レイアウトでの性能計測の追加が求められています。
- `DispatchStubLong` は40→48バイトに増加しており、レビューではこれがメモリコストになる点が指摘されています。
