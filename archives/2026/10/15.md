#### 概要
PEMパース処理において、ラベルが空（`-----BEGIN -----`）の場合に、パース再開位置が進みすぎて有効なPEMを検出できなくなる問題を修正するPRです。#133137 で導入された「失敗が確定している内容の再パースを避ける」ための再開位置の最適化が、空ラベルという限定的なケースで先に進みすぎていました。

例えば次のようなPEMで問題が発生していました。

```
-----BEGIN -----BEGIN TEST-----\nZm9v\n-----END TEST-----
```

- 最初に `-----BEGIN -----`（空ラベルの有効なPreEB）が見つかるが、直後の `BEGIN TEST-----` が不正なBase64として扱われる。
- 修正前は `BEGIN TEST-----\n...` からパースを再開していたため一致せず、有効なPEMを見逃していた。
- 2つのPreEBは境界を共有しているため、空ラベルが最初に見つかった位置から再開する必要がある。
- 同様の修正が終端（EndEB）の探索側にも適用されています。

#### 変更内容
- `src/libraries/Microsoft.Bcl.Cryptography/src/System/Security/Cryptography/PemEncoding.cs`: 再開位置の計算を修正（+11/-9）
- `src/libraries/System.Security.Cryptography/src/System/Security/Cryptography/PemEncoding.cs`: 同様の修正（+11/-9）
- `src/libraries/Microsoft.Bcl.Cryptography/tests/PemEncodingFindTests.cs`: 回帰テストを追加（+30）
- `src/libraries/System.Security.Cryptography/tests/PemEncodingFindTests.cs`: 回帰テストを追加（+30）

影響なし（再開位置の補正のみで、ベンチマーク結果の記載もありません）。

原因は、テストが独自に宣言した `nuint` 2フィールドの `RLimit` 構造体を libc の `getrlimit`/`setrlimit` に P/Invoke していた点です。この構造体は arm32 で 8 バイトですが、musl は全アーキテクチャで `rlim_t` を `unsigned long long` と定義しており、`struct rlimit` は 16 バイトになります。このため `getrlimit` が構造体の範囲外に書き込み、`setrlimit` は `newLimit` の後続 8 バイトからハードリミットを読んで失敗することがありました。glibc の arm32 では `rlim_t` が 32-bit のため一致していました。

修正は、System.IO.FileSystem 等のテストと同様に、System.Native の `Interop.Sys.GetRLimit`/`SetRLimit` を使う形に変更するものです。System.Native が2つの `ulong` の `RLimit` をプラットフォームの `struct rlimit` に変換します。

#### 変更内容
- `src/libraries/System.Diagnostics.Process/tests/ProcessHandlesTests.Unix.cs`（+16/-25）
  - 独自の `RLimit` 宣言と libc への P/Invoke を、`Interop.Sys.GetRLimit`/`SetRLimit` に置き換え

  - 下げたリミットは返された `MaximumLimit` を維持
  - 呼び出し失敗時は errno 付きの `Win32Exception` をスロー（`dup2` の既存処理と同様）
- `src/libraries/System.Diagnostics.Process/tests/System.Diagnostics.Process.Tests.csproj`（+2/-0）
  - `Interop.ResourceLimits.cs` の共有インターロップをコンパイル対象に追加

}

    }
    finally
    {
        for (int i = 0; i < 1_000; i++)
        {
            Thread.SpinWait(1);
        }
    }
}

- 作成者: [@Dev-next-gen](https://github.com/Dev-next-gen)
- 作成日時: 2026年09月11日 04:48:42(UTC)
- マージ日時: 2026年10月15日 08:50:57(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-System.Net.Http/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-System.Net.Http</span></a> <a style="text-decoration:none;" href="../../labels/community-contribution/index.html"><span style="background-color: #c2e0c6; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">community-contribution</span></a>
#### 概要
マネージド実装の `HttpListener` がリクエスト解析時に、LF を伴わない単独の CR（bare CR）を黙って捨てて前後の文字列を連結してしまう問題を修正します。RFC 9112 §2.2 では、単独 CR を受け取った場合は要素を不正として扱うか CR を SP に置換することが求められており、現状はどちらにも該当しません。本変更では、LF が直後に続かない CR を拒否するようにし、http.sys（Windows）の挙動（400 を返す）に揃えます。

作成者の検証では、以下のようなリクエストがマネージド実装では受理され、http.sys では 400 になっていました。
- `Content-Le\rngth: 5` → `Content-Length: 5` として扱われる
- `X-Test: ab\rcd` → ヘッダー値が `abcd` になる
- `GET /c\rd HTTP/1.1` → `RawUrl` が `/cd` になる
- `Host: localhost\r\r\n` → 受理される
- チャンクサイズ行 `1\r0\n` → 0x10 バイトのチャンクとして読まれる

#### 変更内容
- `ChunkStream.cs`（+7/-4）: `GetChunkSize` で、読み取りループの後ろにあり実質到達不能だった `Missing \n` チェックをループ内に移動し、bare CR を検出できるようにしました（`break` なしでループを抜けるのは `offset == size` のときのみで、`offset < size` が成立しないため）。
- `HttpConnection.cs`（+7/-0）: `ReadLine` で、CR の直後が LF でない場合に例外を投げます。`ProcessInput` が既にこの例外を 400 に変換します。
- `InvalidClientRequestTests.cs`（+6/-0）: bare CR を含む 4 件の不正リクエストを追加（実装非依存）。作成者は同じ 4 件が http.sys で 400 になることを確認しています。
- `HttpRequestStreamTests.cs`（+46/-0）: マネージド実装のみを対象とした `Read_ChunkSizeWithBareCR_ThrowsHttpListenerException` を追加。

互換性・挙動について:
- 公開 API は変更なしです。
- 新たに失敗するのは RFC 上不正で、http.sys が既に 400 で拒否しているリクエストのみです。
- 単独 LF による行終端は引き続き許可され、CR と LF が複数回の読み取りに分割されるケースも従来どおり動作します。
- 作成者の説明では、#132163 / #132747 で空白について対処した「中継装置との解釈不一致」と同種の問題を塞ぐものです。
