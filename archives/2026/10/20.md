#### 概要
ILVerifyが、配列ではないオペランド（例: string）を `ldelem.*` / `stelem.*` / `ldelema` に渡された場合に `InvalidCastException` でクラッシュする問題を修正します。修正後は `ExpectedArray` を報告し、そのメソッドの検証を中断します。また、null配列に対する有効な `ldelem.ref` で `NullReferenceException` が発生する問題も修正します。

クラッシュを再現するILの例:

```il

{
    ldstr "a"
    ldc.i4.0
    ldelem.i4
    pop
    ret
}
```

- `src/coreclr/tools/ILVerification.Tests/ILTests/ArrayTests.il` (+87/-0)
  - テストメソッドを9件追加しました。
    - stringを配列オペランドとする `_Invalid_ExpectedArray` が7件（`ldelem.i4`、`ldelem.ref`、`ldelem <token>`、`stelem.i4`、`stelem.ref`、`stelem <token>`、`ldelema`）
    - `int32` を配列オペランドとする `ldelem.ref` の `_Invalid_ExpectedArray` が1件
    - null配列に対する `ldelem.ref` の `LoadElement.RefFromNull_Valid` が1件

挙動の変化として、`ldlen` の非配列オペランドや多次元配列への要素アクセスも `CheckIsArray` を通ります。これらは以前もクラッシュせず `ExpectedArray` を報告していましたが、今後はそこで検証を中断します。

影響なし

#### 概要
OpenHarmony 上の CoreCLR で `EnableWriteXorExecute`（W^X）のデフォルト値を 0 にする変更です。

- OpenHarmony のサンドボックスは、ファイルバックのマッピングへの `PROT_EXEC` を拒否します（匿名の実行可能メモリは許可）。そのため実行用ビューを作成できず、JIT コンパイルされたコードを実行できません。

- `src/coreclr/inc/clrconfigvalues.h`
  - `EXTERNAL_EnableWriteXorExecute` を囲むガードを `#ifdef TARGET_RISCV64` から `#if defined(TARGET_RISCV64) || defined(TARGET_OPENHARMONY)` に変更し、両ターゲットでデフォルトを 0 にしました。
  - サンドボックス上の理由を示すコメント 2 行と、末尾の `#endif` コメントを追加しました。
  - 差分は 4 行追加・2 行削除です。

- ランタイムの内部設定（CLR config のデフォルト値）の変更で、公開 API の変更ではありません。
- `TARGET_OPENHARMONY` は #132953 のプラットフォームビルドサポートで定義されます。RISC-V を含む他のターゲットは従来どおりの分岐を通り、デフォルト値 1 を維持します。
- マネージド API、ビルド、テストの変更はありません。互換性への影響は OpenHarmony ターゲットのデフォルト動作のみです。

#### パフォーマンスへの影響
ベンチマーク結果の記載はありません。W^X を無効化するデフォルト（RWX アロケーター）への切り替えであり、OpenHarmony 以外のターゲットには影響しません。PR の主眼は性能ではなく、JIT コードを実行可能にすることです。

- 実機の直接プローブでは、memfd マッピングへの `PROT_EXEC` 付与（`mprotect`）は `EACCES` を返す一方、匿名マッピングは RW から RX に切り替えて実行できました。
