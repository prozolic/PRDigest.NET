- マージ日時: 2026年10月22日 11:28:31(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-System.Net/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-System.Net</span></a>
#### 概要
`ContentType.Name` / `ContentDisposition.FileName` のシリアライズ時に、値が RFC 2047 のエンコード済みワードで始まるだけで「エンコード済み」と見なされ、引用符内にそのまま追記されていたため、`"` を含む値で MIME パラメータ（例: `filename`）をヘッダーに注入できる問題への対策です。エンコード済みワード判定の厳格化と、非該当値を `GetTokenOrQuotedString`（引用符のエスケープ処理あり）へ回す方針が中心です。

```csharp
var ct = new ContentType("application/octet-stream");
ct.Name = "=?utf-8?Q?foo?=?evil\"; filename=\"foo.txt";
// 修正前: application/octet-stream; name="=?utf-8?Q?foo?=?evil"; filename="foo.txt"
// （攻撃者が制御する filename パラメータが注入される）
```

#### 変更内容
- `MimeBasePart.DecodeEncoding`（ファイルは変更一覧に含まれず、PR説明・レビュー記載による）: 値全体が、折り返し空白のみで区切られた1つ以上の RFC 2047 エンコード済みワードである場合にのみ非 null を返すよう厳格化。`SearchValues<char>` を用いた文字検証へリファクタリング。
- `ContentType.cs`（+1/-1）、`ContentDisposition.cs`（+7/-0）: `EncodeToBuffer` の「手動エンコード済みとしてそのまま通す」分岐を、有効なエンコード済みワードの場合のみ到達するよう調整。
- `Attachment.cs`（+15/-2）、`Strings.resx`（+7/-1）: 変更あり（詳細は提供情報からは不明）。
- テスト: `ContentTypeTest`、`ContentDispositionTest`、`AttachmentTest`、`AlternateViewTest`、`QuotedPrintableStreamTest` に、注入ペイロードおよび正当なエンコード済みワードのラウンドトリップを検証するテストを追加。

#### その他
- 本PRは `System.Net.Mail` のヘッダーパラメータ注入に対するセキュリティ強化です（CVE番号の記載なし）。
- Copilotレビューでは、整形式のエンコード済みワードでも encoded-text に `"` や `\` が含まれ得るため、パススルー分岐が依然として引用符を抜け出して注入を許す可能性があると、複数回指摘されています（例: 空白なしの `=?utf-8?Q?foo";filename="x?=`）。対策として、パススルー前のエスケープ、またはこれらの文字を含む値をパススルー対象外にする案が挙がっています。
- 最新のレビューでは、`ContentType` のエスケープ関連テストが、デコードを行うゲッターに対して生のエンコード済みテキストを期待している点も指摘されています。
