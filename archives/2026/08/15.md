### [#132345](https://github.com/dotnet/runtime/pull/132345) Restore Windows Arm64 support for CPUs without LSE {#132345}
- 作成者: [@tannergooding](https://github.com/tannergooding)
- 作成日時: 2026年08月14日 22:09:34(UTC)
- マージ日時: 2026年08月15日 16:46:00(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-VM-coreclr/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-VM-coreclr</span></a>
#### 概要
Windows Arm64ランタイムにおいて、LSE（Large System Extensions）をオプション機能として扱い、基本CPU要件をArmv8-Aに戻します。これにより、LSEなしのNXP i.MX 8プロセッサを搭載したWindows 10 IoTデバイスでの実行をサポートしながら、ReadyToRunの基準はArmv8.2-A + RCPCのままとします。LSEなしのハードウェアではR2Rイメージが拒否され、JITにフォールバックします。

#### 変更内容
- **cpufeatures.c**: Windows Arm64でLSEをオプション機能として扱い、存在する場合は機能を報告するが、未実装時はベースライン無効とはしないように修正
- **codeman.cpp**: CoreCLR起動時のエラーメッセージから、Windows Arm64では必須ではないLSEの要件を削除
- **InstructionSetHelpers.cs**: NativeAOT向けの非R2R ARM64ビルドから、Windows固有のLSEベースライン要件を削除
- **startup.cpp**: NativeAOT起動時のエラーメッセージをCoreClrに合わせて更新

#### パフォーマンスへの影響
影響なし

#### 関連Issue
[#132340](https://github.com/dotnet/runtime/issues/132340)

#### その他
このPRはGitHub Copilotで作成されました。ReadyToRun基準は変更されないため、既存のR2R契約は保持されます。

### [#132302](https://github.com/dotnet/runtime/pull/132302) Add locking for cDAC APIs {#132302}
- 作成者: [@rcj1](https://github.com/rcj1)
- 作成日時: 2026年08月14日 05:02:13(UTC)
- マージ日時: 2026年08月15日 01:14:18(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-Diagnostics-cdac/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-Diagnostics-cdac</span></a>
#### 概要
cDAC（Common Data Access）APIs が同じ `Target` を共有する場合、複数スレッドからの同時アクセスを防ぐため、per-Target の `ApiLock` を導入しました。COM エントリーポイント全体に`Monitor`ベースのロック機構を実装し、スレッド間の再入性を防ぎます。この変更は内部実装（Legacy COM インターフェース層）に限定され、公開 API への直接的な影響はありません。

#### 変更内容
- **Entrypoints.cs**: `Target` と `ApiLock` をペアで保管し、作成される SOS/DacDbi インスタンスへ共有ロックを渡す
- **ComInterfaceLock.cs**: `Monitor` ロックをスコープ化するための軽量 RAII ヘルパー(`IDisposable`)を追加
- **SOSDacImpl.cs 関連**: `_apiLock` フィールドを追加し、IXCLRDataProcess メソッドおよび ICLRDataEnumMemoryRegions メソッドをロック化。外部通知コールバック実行時はロック解放後に呼び出しを実行し、デッドロック回避
- **DacDbi ラッパー群** (ClrDataValue, ClrDataFrame, ClrDataTask, ClrDataModule など): 各 COM メソッドの実装時に `_apiLock` でシリアライズ化。返却されるラッパーオブジェクトへロックを伝播
- **MetaDataImportImpl.cs**: COM メソッドをロック化し、既存の ConcurrentDictionary 使用方法との整合性を改善
- **テストファイル**: 57 個の単体テスト・ダンプテストを更新し、新しい `apiLock` コンストラクタパラメータを供給

#### パフォーマンスへの影響
各 cDAC API 呼び出しは追加の `Monitor.Enter/Exit` オーバーヘッドを被ります。ロック保有時間は極力短縮されています（外部コールバック実行時はロックを解放）。大規模な同時アクセスがない診断シナリオでは影響は軽微と予想されますが、ベンチマーク結果は提供されていません。

#### 関連Issue
なし

#### その他
Copilot の指摘により、以下の潜在的な問題が抽出されています：
- `Entrypoints.cs` の既存ハンドルからのインターフェース作成時、`ValidateForDataAccess()` がロック外で実行され、他の cDAC API との競合リスクが存在
- `MetaDataImportImpl.cs` の `_cdacEnumHandles` ConcurrentDictionary のコメントは、現在はロック保護されているため更新が必要

本変更は共有 `Target` へのシリアルアクセスを保証しますが、レビュー時に指摘された競合条件（特にインターフェース初期化フェーズ）への対応は確認されていません。

### [#132033](https://github.com/dotnet/runtime/pull/132033) Partition the ComWrappers RCW cache into per-processor buckets {#132033}
- 作成者: [@Sergio0694](https://github.com/Sergio0694)
- 作成日時: 2026年08月08日 07:00:06(UTC)
- マージ日時: 2026年08月15日 15:49:56(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-System.Runtime.InteropServices/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-System.Runtime.InteropServices</span></a> <a style="text-decoration:none;" href="../../labels/tenet-performance/index.html"><span style="background-color: #c2e0c6; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">tenet-performance</span></a> <a style="text-decoration:none;" href="../../labels/community-contribution/index.html"><span style="background-color: #c2e0c6; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">community-contribution</span></a>
#### 概要
ComWrappers の RCW（Runtime Callable Wrapper）キャッシュをプロセッサ数に基づいて複数のバケットに分割し、単一の `ReaderWriterLockSlim` による競合を軽減する変更です。キャッシュエントリを `WeakGCHandle<NativeObjectWrapper>` に置き換え、型安全性と処理効率を向上させます。ネイティブ・マネージド間の遷移は非常にホットパスであり、特にファイナライザスレッドによる書き込みとアプリケーションスレッドによる読み込みの競合を解消することで、大幅なパフォーマンス向上が期待できます。

#### 変更内容
- **ComWrappers.cs**: RCW キャッシュをバケット配列に分割。各バケットは独立した `Dictionary` と `ReaderWriterLockSlim` を保有。バケット選択には Fibonacci ハッシュ（`0x9E3779B97F4A7C15` による乗算・シフト）を使用し、ポインタの低位ビットの偏りを補正。`RcwCache` と `Bucket` は `readonly struct` として `ComWrappers` 内にインライン化。`GCHandle` から `WeakGCHandle<NativeObjectWrapper>` に移行。

- **Program.cs**: `ComWrappersNoLockAroundQueryInterface` テストを更新。異なる COM ポインタを使用していたため、パーティション化後に異なるバケットにマップされる可能性があった問題を修正。同じアイデンティティポインタを再利用し、同じバケック内での動作を保証。スレッド結合の成功を明示的にアサート。

#### パフォーマンスへの影響

**改善効果（実測値）:**
- CsWinRT 2.3.0 での単一オブジェクト構築: **−7.4%～−10.5%**
- CsWinRT 3.0.0 での単一オブジェクト構築: **−2.4%～−8.1%**
- 10,000 インスタンス構築（ガベージコレクション並行）: **−6.3%～−12.4%**
- Gen2 コレクション削減: **−26%～−60%**
- マイクロベンチマーク（32スレッド、キャッシュヒット）: **最大13.6倍高速化（0.07x～0.25x）**

**トレードオフ:**
- 単一スレッド且つ大規模ワーキングセット（1024 RCW）での低下: **+1%～+11%**（キャッシュフットプリント増加による）
- ComWrappers インスタンスあたりのメモリ増加: 576 B → 6,536 B（32コア環境）。バケット数がプロセッサ数に比例。

#### その他
- **実装の詳細**: バケット数は `BitOperations.RoundUpToPowerOf2(Environment.ProcessorCount)` で決定（ConcurrentDictionary の既定値に合致）。インデックス計算にマスク演算を使用し除算を回避。
- **検証**: 3,461 個の相互運用テストが Checked CoreLib で合格。`RegisterWrapperForObject` のアサーションでキャッシュのバケット選択を直接検証。
- **内部実装の変更**: `RemoveAll` が原子的でなくなったが、呼び出し
