#### 概要

cDAC（Common Data Access Component）の `IData` カスタム初期化方式を、単一の eager `OnInit` フックから名前付きの遅延初期化メソッド（`[CustomInit]` 属性経由）へリファクタリングしました。プロパティへのアクセス時にのみ初期化ロジックが実行され、結果がメモ化されます。これにより、不要な初期化処理を回避し、パフォーマンスを改善します。

```csharp
// 従来の方式（削除）
public void OnInit() { /* 全プロパティの初期化ロジック */ }

// 新方式（追加）
[CustomInit(nameof(InitializeProperty))]
public required string Property { get; init; }

private string InitializeProperty() { /* 当該プロパティのみの初期化ロジック */ }
```

#### 変更内容

**コア機能変更：**
- `CdacAttributes.cs`: 新しい `[CustomInit]` 属性を公開APIとして追加
- `Parser.cs`, `Model.cs`, `Emitter.cs`: ジェネレータが `[CustomInit]` を解析し、遅延メモ化ゲッターを生成するよう対応
- `UsageWalker.cs`, `CdacAttributeMatcher.cs`: 使用分析ツール（CdacUsageGraph）が初期化メソッドを依存関係として認識し、メソッド本体も走査

**IData実装の変換（20+ ファイル）：**
- 既存の `OnInit` 実装を名前付きメソッドに分割（Thread, UnwindInfo, TypeDesc, SyncBlock, RCW, Bucket等）
- オプションフィールドの遅延読み取り対応
- `TableRW` にディスクリプタのみの型を追加（メタデータテーブルインデックス時のサイズ計算用）

**ドキュメント・テスト：**
- `IData.md`: 仕様書を更新（`[CustomInit]` による遅延初期化を説明）
- データコントラクト設計ドキュメント再生成（プロパティレベルの遅延読み取りを反映）
- ジェネレータテスト: 46パス、使用分析テスト: 86パス、統合テスト: 3207パス（16スキップ）

#### パフォーマンスへの影響

影響なし（理論的な改善はあるが、定量的ベンチマークは提供されていない）

**改善ポイント：**
- 実際に使用されるプロパティのみ初期化ロジックが実行される
- 不要な計算（ポインタ追跡、バッファ読み込み、レジスタマップ構築等）の遅延実行
- メモ化により、同じプロパティへの重複アクセスで計算を回避

[#131763](https://github.com/dotnet/runtime/issues/131763)

### [#130664](https://github.com/dotnet/runtime/pull/130664) Fix TransactionManager DefaultTimeout/MaximumTimeout setter race condition {#130664}
- 作成者: [@Copilot](https://github.com/apps/copilot-swe-agent)
- 作成日時: 2026年07月14日 04:46:46(UTC)
- マージ日時: 2026年08月03日 21:12:19(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-System.Transactions/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-System.Transactions</span></a>
#### 概要
`TransactionManager.DefaultTimeout` および `MaximumTimeout` のセッターに競合状態が存在していた問題を修正しました。ゲッターが `LazyInitializer.EnsureInitialized` でロックを取得する一方、セッターが `Interlocked.Exchange` と平文の書き込みを使用していたため、別スレッドのゲッターが新しい値を上書きする可能性がありました。すべての処理をロック下で実行することで状態の一貫性を確保し、競合状態を排除しました。

#### 変更内容
- **TransactionManager.cs**: DefaultTimeout および MaximumTimeout の getter/setter の実装を変更。すべての読み書き操作を `s_classSyncObject` ロック下で実行するように統一。
- **設定ファイル削除**: .NET Framework の設定システムの遺産である以下の設定ファイルを削除
  - ConfigurationStrings.cs
  - DefaultSettingsSection.cs
  - MachineSettingsSection.cs
  - System.Transactions.Local.csproj 内の設定参照

#### パフォーマンスへの影響
DefaultTimeout/MaximumTimeout のプロパティアクセス時はロック取得が必要となるため、競合状態が高い環境ではわずかなオーバーヘッドが生じる可能性があります。ただし、これらのプロパティは通常、アプリケーション起動時に設定されるため、実運用への影響は最小限と考えられます。
