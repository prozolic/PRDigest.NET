#### 概要
Helix Job Monitor有効時に、ライブラリのHelix送信を独立したテスト実行ジョブから統合CoreCLR/librariesビルドジョブへ移動します。これにより、13個のアーティファクト専用テスト実行ジョブを削除し、ライブラリテストアーティファクトの発行とダウンロードのオーバーヘッドを回避します。プラットフォームマトリックス、Helixキュー、条件、実行時構成、テスト実行名は維持されます。

- **eng/pipelines/runtime.yml**：既存ビルドジョブにライブラリHelix送信を統合し、スタンドアロンのlibrariesテスト実行ジョブマトリックスを削除。パス基準の変更検出変数（`librariesContainsChange`、`coreclrContainsChange`）を追加してHelix送信を制御。
- **eng/pipelines/libraries/helix.yml**：`helixBuildConfig`パラメータを追加し、Helix `/p:Configuration`をプロデューサージョブのビルド構成から切り離す。これにより、ビルド構成が異なるプロデューサージョブ向けに別途の送信構成を指定可能に。

なし

- 既存のプラットフォームマトリックス、Helixキュー、条件、実行時構成、テスト実行名はすべて保持され、外部への影響は最小限に抑えられています

#### 概要
カスタム struct awaiterの呼び出しで発生していたボックス化を排除する最適化です。awaiterを継続オブジェクト内に格納し、JITが計算したオフセットで後に抽出してから`UnsafeOnCompleted`を呼び出すことで、ボックス化を回避します。新たに`GT_CONTINUATION_MEMBER_OFFSET`ノードを導入し、オフセットが確定するまで象徴的に参照してから定数に置換します。

マイクロベンチマークでは約10%のパフォーマンス改善が確認されています。

```csharp
// 最適化により、struct awaiterの格納と抽出がボックス化なしで行われます
await new CustomStructAwaiter(value);
```

#### 変更内容
- **AsyncHelpers.cs**: 継続内の awaiter をオフセット指定で待機する新しいヘルパーメソッド追加
- **async.cpp/async.h**: `GT_CONTINUATION_MEMBER_OFFSET`ノードを使用した継続レイアウト管理と、awaiter の継続内への格納・抽出ロジック実装
- **importercalls.cpp**: struct awaiter の呼び出しを新しいヘルパーに書き換え、継続メンバーオフセットを記録
- **JIT↔EE インターフェース**: 新しいヘルパーメソッド解決用の仮想メソッド追加(`ICorStaticInfo::getAwaitAwaiterInContinuationCall`)
- **jitinterface.h/cpp**: ヘルパー解決ロジック実装
- **SuperPMI**: 新しいクエリのプラミング（shim/collector/recorder）
- **ILC/ReadyToRun**: トークン解決対応
- **テスト**: `custom-struct-awaiters.cs`で safe/unsafe struct awaiter の回帰テスト追加
- **jitconfigvalues.h**: 継続再利用の設定可能化を削除（無条件有効化）

#### パフォーマンスへの影響
マイクロベンチマーク結果：
- **約10%改善** (323ms → 290ms)
- ボックス化の排除により、struct awaiter を使用した大量の`await`呼び出しで顕著な改善
- メモリ効率向上（GC圧力低減）

#### 関連Issue
[#119842](https://github.com/dotnet/runtime/issues/119842)

#### その他
- **内部実装変更**: JIT コンパイラの async 変換パイプラインのみに影響、パブリック API に変更なし
- **継続再利用**: 従来は設定可能だった`GT_CONTINUATION_MEMBER_OFFSET`展開の単純化のため、継続再利用を無条件で有効化
- **新しい well-known arg**: `AsyncAwaiter`という新しいの pseudo arg を導入し、async 変換で継続オブジェクトのオフセットに配置

### [#131177](https://github.com/dotnet/runtime/pull/131177) Remove queue-subdispatching pattern to the ThreadPool global queue  {#131177}

#### 概要

Socket/IO完了イベントのThreadPool派遣パターンを変更します。従来の「キュー+ポンピングワークアイテム」パターンを廃止し、プール化されたワークアイテムをバランス二分木で束ねてバッチ送信する方式に置き換えます。これにより、グローバルキューへの負荷軽減、メモリ境界設定、p99レイテンシの大幅な改善を実現します。

#### 変更内容

- **ThreadPoolWorkQueue.cs**: Windows専用の`ThreadPoolTypedWorkItemQueue`サブディスパッチャー実装を削除
- **PortableThreadPool.IO.Windows.cs**: IOCP完了用に`Event`ワークアイテムをプール化し、バランス二分木でバッチ送信。ノード実行時に子をローカルキューに配置
- **SocketAsyncEngine.Unix.cs**: `SocketIOEvent`インスタンスをプール化し、非同期ソケットイベントを同様にバランス二分木でバッチ送信。ローカル優先スケジューリングを調整
- **SocketAsyncContext.Unix.cs**: 非同期操作処理/キャンセルコールバックの一部を`preferLocal: true`でキューイング
- **PortableThreadPool.HillClimbing.cs**: HillClimbingロジックの軽微な調整
- **SafeSocketHandle.Unix.cs**: Unix固有の調整

#### パフォーマンスへの影響

**改善**: JSON ベンチマーク（56コア）
- RPS: +2.1%（2,528,080 → 2,580,722）
- p99レイテンシ: **-17.4%**（3.79ms → 3.13ms）

**改善**: JSON ベンチマーク（96コア/低負荷）
- RPS: +4.1%（2,064,045 → 2,149,487）
- p99レイテンシ: **-43.6%**（0.78ms → 0.44ms）

**改善**: JSON ベンチマーク（96コア/高負荷）
- p99レイテンシ: -4.0%（7.30ms → 7.01ms）

高コア数構成でのp99レイテンシ改善が特に顕著。.NET 10との性能差をほぼ解消。

#### 関連Issue

[#127484](https://github.com/dotnet/runtime/issues/127484)

#### その他

**実装上の懸念点**: Copilot によるコードレビューで、`ConcurrentQueue<T>.Count`をホットパス（毎回のIO完了/イベント実行）で呼び出すことが指摘されています。Count操作は競合下で高コストになる可能性があるため、`Interlocked` ベースのカウンタに置き換えることが推奨されています。

**互換性**: 内部実装の変更であり、公開APIへの破壊的変更はなし。
