### [#131714](https://github.com/dotnet/runtime/pull/131714) Avoid inlining Random.InternalSample {#131714}
- 作成者: [@AndyAyersMS](https://github.com/AndyAyersMS)
- 作成日時: 2026年08月02日 15:46:03(UTC)

#### 概要
`Random.InternalSample()`メソッドに`[MethodImpl(MethodImplOptions.NoInlining)]`属性を追加し、メソッドのインライン化を抑止する変更です。このメソッドは予測不可能な分岐を含んでおり、ループ内でインライン化されるとif変換が行われずパフォーマンスが低下するため、スタンドアロンメソッドとして保持することを意図しています。

#### 変更内容
- **src/libraries/System.Private.CoreLib/src/System/Random.CompatImpl.cs**
  - `CompatPrng.InternalSample()`メソッドに`[MethodImpl(MethodImplOptions.NoInlining)]`属性を追加
  - インライン化を避ける理由を説明するコメントを追加

#### パフォーマンスへの影響
改善あり。ホットループ内でのメソッド呼び出し時に以下の改善が期待できます：
- メソッドをインライン化しないことで、JITコンパイラがif変換を適用可能
- if変換により、分岐予測が困難な条件分岐が消去され、実行速度が向上
- 特にランダム値生成が頻繁に呼び出されるループシナリオで効果的

#### 関連Issue
[#117787](https://github.com/dotnet/runtime/issues/117787)
[#130359](https://github.com/dotnet/runtime/issues/130359)

#### その他
- 変更はランタイムライブラリの内部実装（`System.Random`の互換PRNG）に限定
- 公開APIレベルでは互換性に影響なし
- 将来的にJITのif変換がループ内での制約から解放された場合は、この属性の再検討が可能

### [#131704](https://github.com/dotnet/runtime/pull/131704) Remove temporary array allocations in `ComVariant.As`. {#131704}
- 作成者: [@teo-tsirpanis](https://github.com/teo-tsirpanis)
- 作成日時: 2026年08月01日 23:28:32(UTC)
- マージ日時: 2026年08月02日 05:36:13(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-System.Runtime.InteropServices/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-System.Runtime.InteropServices</span></a> <a style="text-decoration:none;" href="../../labels/community-contribution/index.html"><span style="background-color: #c2e0c6; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">community-contribution</span></a>
#### 概要
`ComVariant.As<T>()`メソッド内の型チェック関数`ThrowIfNotVarType`を改善し、毎呼び出しで発生していた一時的な配列割り当てを削除しました。`params VarEnum[]`から`params ReadOnlySpan<VarEnum>`に変更することで、RVAフィールドへの割り当てフリーな参照として最適化されるようになります。

#### 変更内容
- **src/libraries/System.Private.CoreLib/src/System/Runtime/InteropServices/Marshalling/ComVariant.cs**
  - `ThrowIfNotVarType`ユーティリティ関数のシグネチャを`params VarEnum[]`から`params ReadOnlySpan<VarEnum>`に変更
  - `Array.IndexOf(...)`から`ReadOnlySpan<T>.Contains(...)`に置き換え（例外スロー時のみ`ToArray()`でスパンを具体化）
  - 例外発生時の動作は変わらず、エラーメッセージ生成時のみ配列化

#### パフォーマンスへの影響
**改善あり** - `ComVariant.As<T>()`の呼び出し時に毎回発生していた一時的な配列割り当てが削除されます。特に高頻度で呼び出されるシナリオでは、メモリ割り当て圧力とGC負荷が軽減されます。例外経路（エラーケース）では`ToArray()`による小規模な割り当てが発生しますが、これは例外スロー時の限定的なパスのため全体的なパフォーマンスへの影響は最小限です。

#### 関連Issue
[#131704](https://github.com/dotnet/runtime/issues/131704)

#### その他
この変更はCOM相互運用機能（`System.Runtime.InteropServices.Marshalling`）における内部実装の最適化で、パブリックAPIには影響しません。正常系での割り当てフリー化と例外経路の適切な処理により、パフォーマンスと可用性のバランスが取れた改善となっています。

### [#131585](https://github.com/dotnet/runtime/pull/131585) Flush after each live enumerable write in SSE & JSON {#131585}
- 作成者: [@MihaZupan](https://github.com/MihaZupan)
- 作成日時: 2026年07月30日 12:56:18(UTC)
- マージ日時: 2026年08月02日 07:02:48(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-System.Net/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-System.Net</span></a>
#### 概要
非同期列挙可能の`Stream`へのシリアライズ時に、各要素/イベント出力後に明示的にFlushを実行することで、IISのようなバッファリング層を挟んでも"live"な出力が消費側から即座に観測可能になるようにします。Kestrelや`NetworkStream`は自動Flushするため問題ありませんが、バッファリングを行う実装に対応する必要があります。

#### 変更内容
- **System.Text.Json**: JSON Lines形式での非同期列挙シリアライズで、各値書き込み後に`FlushAsync`を呼び出す
- **System.Net.ServerSentEvents**: 各SSEイベント書き込み後に宛先`Stream`をFlushし、ドキュメントにもその動作を記載
- **PooledByteBufferWriter**: `PipeWriter.FlushAsync`で基底の`Stream`もFlushするよう修正
- **テスト**: 非同期列挙ストリーミングのFlushタイミング検証テストを追加し、テストヘルパーのパラメータ名を改善

#### パフォーマンスへの影響
懸念事項あり: `PooledByteBufferWriter.FlushAsync`がすべてのFlushで`Stream.FlushAsync`を呼び出すようになったため、バッファリングしきい値ベースのFlushも含め、非ストリーミングペイロードに対して余分なFlush syscallが増加する可能性があります。

#### 関連Issue
[#121003](https://github.com/dotnet/runtime/issues/121003)

#### その他
Copilotレビューで3件の低信頼度コメントが抽出されました：
1. `FlushTrackingStream.OnFlush`の非nullable宣言と実装の不一致
2. テストの30秒WaitAsyncタイムアウトがCI失敗時に遅延を招く可能性
3. Stream Flush呼び出しの適用範囲をストリーミングケースに限定するか検討が推奨されています
