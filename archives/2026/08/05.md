- 作成者: [@Copilot](https://github.com/apps/copilot-swe-agent)
- 作成日時: 2026年08月05日 01:58:00(UTC)
- マージ日時: 2026年08月05日 11:16:50(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-System.Net/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-System.Net</span></a>
#### 概要
`BufferBuilder.EnsureBuffer`のバッファサイズ計算で符号付き整数のオーバーフローが発生していた問題を修正します。約1.5GB以上のバッファサイズで計算がオーバーフローし、割り当てサイズが不足して診断困難な例外が発生していました。符号なし整数演算に切り替え、倍化処理を`Array.MaxLength`でクランプすることで、オーバーフローを防止します。

修正前後の計算ロジック：
```csharp
// 修正前：符号付きint演算でオーバーフロー可能
byte[] newBuffer = new byte[((_buffer.Length * 2) > (_buffer.Length + count)) ? (_buffer.Length * 2) : (_buffer.Length + count)];

// 修正後：uint演算 + Array.MaxLength制限
byte[] newBuffer = new byte[Math.Max((uint)_buffer.Length + (uint)count, Math.Min((uint)Array.MaxLength, 2 * (uint)_buffer.Length))];
```

#### 変更内容
- **src/libraries/System.Net.Mail/src/System/Net/BufferBuilder.cs**
  - `EnsureBuffer`メソッドのバッファサイズ計算ロジックを修正
  - 符号付き`int`演算から符号なし`uint`演算に変更
  - バッファサイズの倍化時に`Array.MaxLength`でクランプ処理を追加

#### パフォーマンスへの影響
オーバーフロー閾値未満での動作変更なし。オーバーフロー閾値以上でのみ、正確な例外処理が実現されます。

### [#131138](https://github.com/dotnet/runtime/pull/131138) Strictly require CRLF when parsing HTTP/1.1 chunked encoding lines {#131138}
- 作成者: [@Copilot](https://github.com/apps/copilot-swe-agent)
- 作成日時: 2026年07月21日 10:27:47(UTC)
- マージ日時: 2026年08月05日 11:31:16(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-System.Net.Http/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-System.Net.Http</span></a>
#### 概要
RFC 9112に準拠するため、HTTP/1.1チャンク転送エンコーディングのパース処理を厳密化しました。これまで`SocketsHttpHandler`はチャンクサイズ行とチャンク終端に単一の`LF`（改行のみ）を許容していましたが、仕様により`CRLF`（改行+キャリッジリターン）を厳密に要求するように変更しました。

#### 変更内容
- **HttpConnection.TryReadNextChunkedLine**：チャンクサイズ行とチャンク終端で`CRLF`を厳密に要求するよう実装変更。単一の`LF`やバイト列末の`CR`（`LF`に続かない）を検出時は拒否。`MaxChunkBytesAllowed`の制限と部分バッファ処理は変わらず。
- **Strings.resx**：新しいエラーメッセージリソース`net_http_invalid_response_chunk_line_ending`を追加。不正なチャンク行終端時に`HttpIOException(InvalidResponse)`として投げられます。
- **テスト**：新規テストクラス`SocketsHttpHandler_ChunkedEncodingParsing_Test`で有効な`CRLF`パターン（チャンク拡張、トレーラー含む）と、複数位置での単一`LF`拒否、サイズ行/拡張内のバイト`CR`拒否をカバー。

#### パフォーマンスへの影響
影響なし。チャンク行の終端検出ロジック最適化の一環ですが、パフォーマンス上の改善は明記されていません。

#### 関連Issue
[#131138](https://github.com/dotnet/runtime/issues/131138)

#### その他
チャンク**トレーラー**（`0\r\n`後）はヘッダーパーサーで処理され、仕様に準じて従来通りの寛容な解析が継続されます（本変更はチャンクサイズ行と終端のみに適用）。これは**破壊的変更**となり、単一`LF`終端のチャンク応答を送信するレガシーサーバーからのレスポンスは拒否されるようになります。
