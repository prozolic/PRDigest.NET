- **テスト**: ReadyToRun のコード生成テスト（ストアの省略／保持を最適化有無で確認）、cDAC のアンワインド／StackWalk／R2RInfo テスト、`WasmGCLiveness` による例外帰属テストを追加・更新。

#### パフォーマンスへの影響

- Brotli: -0.16%、gzip: -0.23%、モバイルのコールドダウンロード: -0.09%
- 起動時間: デスクトップ cold -0.2%、warm +2.8%、モバイル cold +0.7%、warm +3.2%、デスクトップのウォークスルー -1.2%

サイズは小幅に削減されましたが、タイミング結果は混在しノイズも大きく、作者自身も性能改善が立証されたとは言えないとしています。`StaticsHelpers.GetGCStaticBase` では7バイトの `local.get 0; i32.const 1; i32.store offset=4` が削除されています。

#### 概要
Linux上の `Process.HandleCount` の性能改善です。従来は `Directory.GetFiles("/proc/<pid>/fd")` で数えていましたが、これは各エントリ（すべてシンボリックリンク）に対して `FileSystemEntry.Initialize()` が eager に `stat` を実行するため、ファイル記述子の数に比例してコストが増えていました（記述子3,000個で1回あたり約8ms・約290KB）。これを `Interop.Sys.OpenDir()`/`ReadDir()`/`CloseDir()`（`stat` を行わない）で数える実装に置き換えています。なお、当初含まれていた「スレッド情報の読み取り遅延（Part 2）」は #137497 に分離されています。

- 発見の経緯: OpenTelemetryでプロセスメトリクスを収集するASP.NET Coreアプリのプロファイルで、`HandleCount` がメトリクス収集で最もコストの高い部分（負荷時にプロセスCPU時間の約0.6%）だったことによる

#### 変更内容
- `Process.Linux.cs`: `HandleCount` の算出を、`OpenDir`/`ReadDir`/`CloseDir` による列挙に変更。`.` と `..`、および現在のプロセスでは列挙自体が開く記述子をスキップ
- `System.Diagnostics.Process.csproj`: 関連するソース追加（+2行）
- `ProcessTests.Unix.cs`: テスト4件を追加
  - `HandleCount_OtherProcess_MatchesFileDescriptorDirectory`
  - `HandleCount_CurrentProcess_IncreasesWhenFilesAreOpened`
  - `Threads` が他の情報を読んだ後も利用可能であることを確認するテスト2件
  - ※著者によれば、Linux向けの共有フレームワーク/テスト基盤をビルドできなかったため、テストは構文確認のみで未実行（CIが初回実行）

**挙動の変更**
1. `HandleCount` がディレクトリを指す記述子も数えるようになった（`Directory.GetFiles()` は副作用的に除外していた）。ディレクトリ記述子を1つ持つプロセスでは値が1大きくなり、`/proc/<pid>/fd` や、全ハンドルを数えるWindowsと整合する
2. 権限不足（他ユーザーのプロセス等）で `/proc/<pid>/fd` を開けない場合、引き続き `UnauthorizedAccessException` をスローするが、メッセージは `Access to the path '/proc/1/fd' is denied.` からOS由来の `Permission denied` に変わる

### [#136612](https://github.com/dotnet/runtime/pull/136612) JIT: forward byref-exposed stores to same-address loads in value numbering {#136612}
- 作成者: [@lewing](https://github.com/lewing)
- 作成日時: 2026年10月28日 22:42:07(UTC)
- マージ日時: 2026年11月13日 20:30:39(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-CodeGen-coreclr/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-CodeGen-coreclr</span></a>
#### 概要
JITの値番号付け(Value Numbering)において、不明なアドレスへのストア(`STOREIND`、フィールド・配列要素・ローカル以外)の直後に同一アドレスから同型の値をロードする場合、ストアした値をそのまま転送(forward)する最適化です。従来は不透明なメモリ変更として扱われ、直前に書き込んだアドレスからの再ロードにも新しいVNが割り当てられていました。既存コメントにあった `VNF_ByrefExposedStore` のアイデアを実装したものです。

- 対象は非volatileの int/long/float/double/ref/byref ストア(longは分解される環境では除外)
- ストアのアドレスと値を保持するメモリ状態を記録し、そのメモリ状態が現在有効な間、同一のliberalアドレスからの同型ロードはストア値を取得
- byref-exposedとGCヒープのメモリ状態が異なる場合にも適用

#### 変更内容
- `src/coreclr/jit/valuenum.cpp` (+81/-15): `fgValueNumberStore` 等でストア情報を記録し、同一アドレスのロードに値を転送。conservativeアドレスも一致する場合、ストア側で既にnullフォルトが発生済みのため、ロードのVNから `NullPtrExc` を省略(VNはIRフラグを変更しない)
- `src/coreclr/jit/valuenumfuncs.h` (+1/-0): `VNF_ByrefExposedStore` 関連の関数定義を追加
- `src/coreclr/jit/optimizer.cpp` (+5/-0): 転送されたロードにループのメモリ依存を記録し、LICMがストアより上にロードをホイストしないようにする
- `src/tests/JIT/opt/ValueNumbering/ByrefStoreForwarding.cs/.csproj`: ARM64/X64のdisasmチェック
- `src/tests/JIT/opt/ValueNumbering/ExceptionSets.cs` (+168): 正当性・例外保持のテスト(ループ依存記録を削除すると失敗するホイスト回帰テストを含む)

#### パフォーマンスへの影響
- SuperPMIでコードサイズが全プラットフォームで縮小: arm64 −34 KB/−33 KB、arm −17 KB、x64/x86 各約 −7 KB、wasm −1 KB
- PerfScoreは全コレクションで改善、スループットコストは+0.01〜0.07%
- Wasm R2Rの `Utf8JsonReader.SkipWhiteSpace` で、各ストア後の `_consumed` 再ロード(ループラッチ内)が除去され、単体メソッドのd8計測で64スペースのケースが77 ns → 45 ns
- x64/x86での残りのサイズ増加は、更新後の読み取りがレジスタ経由になることが主因
- 注: 上記SuperPMI数値は、ref/byref対応とxarchのread-modify-writeチェック削除より前のもの

#### 関連Issue
なし

#### その他
- 型が異なる再解釈ロード(例: longストア→doubleロード)は従来通りメモリを読み取ります
- xarchでのread-modify-writeソース用の特別扱いはなく、転送された更新ソースが `op [mem], x` ではなくレジスタを使う場合があります。CSE側でそのようなロードを除外する対応は別PRに分離されています

#### 概要
Background GC（BGC）が破棄されたアロケーションコンテキストをクリアする際に、未使用バイトを正しく計上（retire）していなかったため、`GC.GetAllocatedBytesForCurrentThread()` が実際には発生していない「幻のアロケーション」を報告する問題を修正します。

修正方法は、通常のアロケーションコンテキスト会計処理のパスを再利用することです。Server GC では join を追加し、既存の stop-the-world フェーズ中に指定された1つのワーカーがすべてのコンテキストをちょうど1回だけ retire するようにしています。

- `src/coreclr/gc/allocation.cpp`（+18/-12）: アロケーションコンテキストの会計処理に関する変更

- `src/coreclr/gc/gcinternal.h`（+2/-1）: 内部定義の更新
- `src/coreclr/gc/gcpriv.h`（+2/-0）: 内部定義の追加
- `src/tests/Regressions/coreclr/GitHub_134724/test134724.cs`（+126/-0）: 回帰テストの追加
- `src/tests/Regressions/coreclr/GitHub_134724/test134724.csproj`（+11/-0）: 回帰テスト用プロジェクトの追加
