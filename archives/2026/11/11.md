#### 概要
`MiscTests.MultiClientHostedBuildAndPublish` が `dotnet build`/`publish` を `DotNetCommand.ExecuteWithCapturedOutput` で直接呼び出しており、`-nr:false` が付与されていませんでした。本PRでは、このテストを他のWasm.Build.Testsと同じ `BuildProjectWithoutAssert`（`BuildOptions` / `PublishOptions` 指定）経由に切り替え、`-nr:false` とヘルパーのbinlog出力フォールバックを共通の場所から適用するようにします。

背景として、過去30日間（AzureDevOpsTests）でこのテストのみが以下のエラーで失敗していました（16件のWindows `main` ビルド、直近は11月11日）。

```
System.UnauthorizedAccessException: Access to the path 'BlazorMultiClientHosted.dll' (or '.exe') is denied
```

なお、原因は **未実証の仮説** です。`-nr:false` がないとMSBuildのワーカーノードが残り、サーバーの出力ファイルをロックし続けるためクリーンアップで削除できない、というものです。この変更後も同じ失敗が出るなら、仮説は誤りだったことになります。

#### 変更内容
- `src/mono/wasm/Wasm.Build.Tests/Blazor/MiscTests.cs`（+3/-9）
  - 直接の `DotNetCommand.ExecuteWithCapturedOutput` 呼び出しを `BuildProjectWithoutAssert`（`BuildOptions` / `PublishOptions`）に置き換え
  - コマンドラインはそれ以外変わらず、同じディレクトリ（`_projectDir`）、同じ `NUGET_PACKAGES`、`-p:Configuration`、`-bl` で実行
  - `UseWBTOverridePackTargets` が true に設定されないため、ヘルパーの `WBTOverrideRuntimePack` パスは適用されない
  - binlogファイル名がヘルパーの命名規則に変わる

### [#135553](https://github.com/dotnet/runtime/pull/135553) Enable direct calls in whole-program Wasm R2R {#135553}
- 作成者: [@davidwrighton](https://github.com/davidwrighton)
- 作成日時: 2026年10月09日 23:14:06(UTC)
- マージ日時: 2026年11月11日 15:57:08(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-ReadyToRun/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-ReadyToRun</span></a>
#### 概要
最適化されたWasm ReadyToRunコンパイル（CoreLib含む）で、同一イメージ内の直接呼び出しを有効化します。対象が適格でない場合は間接呼び出しを維持します。コンパイル時に「直接ターゲット＋間接フォールバック」を持つ遅延Wasm呼び出しリロケーションを出力し、呼び出しポリシー確定後に最終化する方式です。

- 実際に公開された呼び出しリロケーションからスケジューリンググラフを導出し、SCC経由でcallee-firstのレベルを計算します。
- 不適格な遅延呼び出しは間接呼び出しに書き換え、影響を受けるコードオフセットとフレームメタデータを調整します。命令サイズの書き換えが不要な場合は既存レイアウトを維持します。
- 直接呼び出しはターゲットの負の奇数フレームIDを渡します。
- 直接呼び出し先やモジュールeager importで保証されるprecode前提条件を省略し、startup-entrypointとrooted済みmanaged-helperの準備クロージャをeager importへ昇格します。
- 従来の2パスパイプライン、`--two-phase-compilation`、ネイティブx86/x64の汎用直接呼び出し実装は削除されています。
- `WholeProgramCompositeBuildMode=1` により、CoreLibを含むランタイムテストのcompositeをサポートします。

オプトアウト: `--disable-deferred-wasm-calls`（SDK経由では `PublishReadyToRunCrossgen2ExtraArgs=--disable-deferred-wasm-calls`）。

#### 変更内容
- **JIT** (`src/coreclr/jit/`): `codegenwasm.cpp`、`emitwasm.cpp`、`emitfmtswasm.h`、`instrswasm.h`、`handlekinds.h`、`lower.cpp` で、遅延呼び出し疑似命令、Wasmフレーム識別ハンドル種別、直接マネージド呼び出し時のフレームID受け渡しを追加。
- **インターフェース**: `corinfo.h`、`CorInfoTypes.cs` に遅延呼び出しリロケーション種別を追加し、`jiteeversionguid.h` を更新。
- **Crossgen2/ReadyToRun**: `DeferredWasmCallProcessor.cs`、`DeferredWasmCallFinalizationPlan.cs`、`DeferredWasmCallRewriter.cs`、`DeferredWasmCallNode.cs` などを新規追加。`MethodWithGCInfo.cs`、`Import.cs` などでeager import昇格・fixupカバレッジ計算を実装。
- **依存関係解析フレームワーク**: `DependencyAnalyzer.cs` / `DependencyAnalyzerBase.cs` に、静止状態（quiescence）フックと、依存関係公開後のマーキング再開機構を追加。
- **VM**: `dllimport.cpp` で、CoreLibがアクティブになる前のWasm eager初期化時に、静的リンクされたCoreLibのP/Invokeターゲット解決を許可。
- **テスト基盤**: `CLRTest.*.targets` でcomposite実行パスを追加。`ILCompiler.ReadyToRun.Tests` に呼び出しポリシー、eager import、フレーム識別などのテストを追加。
- **ドキュメント**: `readytorun-format.md` にfixup昇格と準備保証を記載。

#### パフォーマンスへの影響
Havit Bootstrapでの比較（indirect vs deferred、net12.0）:

- **サイズ**: Composite owner raw 41,192,582 → 40,390,056 B (-1.95%)、Brotli -1.55%、gzip -2.42%。
- **Cold download**: Chrome desktop -1.43%、Chrome mobile -0.73%。
- **起動時間**: Chrome desktop cold 1,516 → 1,415.5 ms (-6.63%)、warm -1.35%、walkthrough -4.76%。Firefox desktop cold -2.75%、warm -1.61%。
- **Mobile warm startup は不安定**: 主計測は +7.05% だが、別のABBA再計測では -3.30%。安定した効果は主張されていません。
- **コンパイラコスト（中央値）**: wall time 14.985 → 16.645 s (+11.08%)、CPU +5.23%、peak RSS +9.00%。出力の縮小と実行時改善との引き換えです。
- 別実験（net11.0）では、compact bookkeepingによりwall -4.14%、CPU -2.70%、peak RSS -11.09%。
- **懸念点**: 静的上限で、fixup occurrenceのp99が26→32、最大準備メソッド上限が86→110に増加。`Statics.CreateDefaultTypeInfo` のメソッド活性化エントリは5→40。レベルポリシーは深さを制約するが、fan-outは制約しません。
