### [#138434](https://github.com/dotnet/runtime/pull/138434) Resolve async-variant IL tokens in the wrapped IL's module {#138434}
- 作成者: [@lewing](https://github.com/lewing)
- 作成日時: 2026年11月27日 19:07:20(UTC)
- マージ日時: 2026年11月27日 23:28:13(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-ReadyToRun/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-ReadyToRun</span></a>
#### 概要
`ReadyToRunILProvider.AsyncMethodIL` は `GetObject` を内部でラップしている IL に転送していましたが、`Module` は常に async バリアントの所有モジュールを返していました。クロスモジュールインライン化のために対象の IL が mutable module 側へ書き換えられている場合（`ManifestModuleWrappedMethodIL`）、crossgen2 は mutable module のトークンを所有モジュールのメタデータに対して解決してしまい、インライン化された async バリアントが無関係なメンバーを参照していました。本変更では、NativeAOT の `EcmaAsyncMethodIL` と同様に、ラップされた IL のモジュールを返すようにしています。

この問題は Wasm 固有ではなく、#138349 で browser ライブラリの runtime async が有効化されたことで顕在化しました。browser-wasm64 のフレームワークコンパイルでは `System.Security.Cryptography` で `ComputeActualOwningType` の assert が発生し、`ValueTask.FromCanceled` の async バリアントが `GCHandle<Action>` のメンバーに解決されていました。browser-wasm32 でも assert は出ないものの同じトークンを誤解決します。

#### 変更内容
- `src/coreclr/tools/Common/TypeSystem/IL/AsyncMethodIL.cs`（新規、+54）: async バリアントの IL ラッパーを共通コードとして追加
- `src/coreclr/tools/Common/TypeSystem/IL/NativeAotILProvider.cs`（+1/-35）: 共通の `AsyncMethodIL` を利用するよう整理（実装を移動）
- `src/coreclr/tools/aot/ILCompiler.ReadyToRun/IL/ReadyToRunILProvider.cs`（+1/-24）: ReadyToRun 側のラッパー実装を共通実装に置き換え
- `ILCompiler.Compiler.csproj` / `ILCompiler.ReadyToRun.csproj`（各 +1）: 共有ソースを参照に追加
- `src/coreclr/tools/aot/ILCompiler.ReadyToRun/JitInterface/CorInfoImpl.ReadyToRun.cs`（+1/-1）: 軽微な修正
- テスト追加: `AsyncVariantInlineeConsumer.cs`、`AsyncVariantInlineeLib.cs`、`R2RTestSuites.cs` に `AsyncVariantCrossModuleInlining` テストを追加

#### パフォーマンスへの影響
影響なし（コンパイラのトークン解決の正当性に関する修正）。

#### 関連Issue
- [#138349](https://github.com/dotnet/runtime/issues/138349)（browser ライブラリの runtime async 有効化。この問題が顕在化した契機として記載）

#### その他
- 新規テスト `AsyncVariantCrossModuleInlining` は、修正なしでは `GetCanceledOrValue` の async バリアントがクロスモジュールインライン化されず失敗し、修正後は成功します。
- 作成者によれば、browser-wasm ビルドに対するローカル実行で `ILCompiler.ReadyToRun.Tests` は 402 件成功、0 件失敗、42 件スキップでした。

#### 概要
`Set-Cookie` ヘッダーに `Expires` と `Max-Age` の両方がある場合、`CookieContainer.SetCookies` は先に現れた属性を採用していました。`CookieParser.Get()` が両者を単一の `expiresSet` フラグで管理していたため、後から現れた属性が無視されていました。RFC 6265 4.1.2.2 / 5.3 step 3 では、順序に関わらず `Max-Age` が優先されます。

#### 変更内容
- `src/libraries/Common/src/System/Net/CookieParser.cs`（+8/-5）
  - `CookieParser.Get()` で `Max-Age` を独自の `maxAgeSet` フラグで追跡
  - パース成功した `Max-Age` は常に有効期限を設定し、`Max-Age` 出現後の `Expires` は無視
  - 不正な値の挙動は従来どおり（パース不能な `Max-Age` は、その前に `Expires` がない限りクッキーを拒否）
- `src/libraries/System.Net.Primitives/tests/FunctionalTests/CookieContainerTest.cs`（+44/-0）
  - 正の `Max-Age` と `Max-Age=0` の両方について、両属性の順序（`Expires` 先／`Max-Age` 先）を検証するテストを追加

影響なし

[#138251](https://github.com/dotnet/runtime/issues/138251)（Fixes）

#### 概要
Linux 6.2以降、`sched_setaffinity`で明示的に設定したCPUマスクがcpusetの変更後も保持されるようになりました。そのため、コンテナのCPU割り当てが `4-5` から `5-6` に変わると、ランタイムのスレッドが意図せずCPU `5` のみに固定される問題が起きていました。このPRは、`CPalThread::ThreadEntry` による新規スレッドへのアフィニティ再設定を削除し、必要なバックグラウンドのサーバーGCスレッドでのみ再設定する形に変更します。通常のスレッドは作成元スレッドのアフィニティを継承します。

#### 変更内容
- `src/coreclr/pal/src/thread/thread.cpp`: `CPalThread::ThreadEntry` でのアフィニティ再設定処理を削除（-77行）
- `src/coreclr/pal/src/config.h.in` / `configure.cmake`: 上記処理に関連する設定・チェックを削除
- `src/coreclr/gc/background.cpp`: バックグラウンドGCスレッド開始時に、メインスレッドの現在のマスクを取得して適用する処理を追加
- `src/coreclr/gc/env/gcenv.os.h`: GC向けのOS抽象インターフェースに宣言を追加
- `src/coreclr/gc/unix/gcenv.unix.cpp`: Unix向けの実装を追加
- `src/coreclr/gc/windows/gcenv.windows.cpp`, `src/coreclr/gc/wasm/gcenv.cpp`: Windows/WASM向けのスタブ（実装）を追加

CoreCLRとNative AOTはこのコードを共有します。

**挙動の変更点**
`Process.ProcessorAffinity` でメインスレッドをCPU `5` に絞った後、CPU `4-5` で動作するスレッドが新しいスレッドを開始すると、新スレッドは `4-5` を継承します（従来はメインスレッドのマスクが適用されていました）。

#### パフォーマンスへの影響
影響なし（ベンチマーク結果の記載はありません）。サーバーGCのアフィニティ設定が有効な場合、各ヒープスレッドは1つのCPUを保持し、バックグラウンドGCスレッドはメインスレッドの現在のマスクを使用します。

#### 関連Issue
[#136015](https://github.com/dotnet/runtime/issues/136015)

#### その他
動作確認：
- Linux 6.18でDockerコンテナのCPUを `4-5` → `5-6` に移動したところ、既存のマネージドスレッド、移動後に開始したスレッド、子プロセスのすべてが `5-6` になることを確認（`4-9` への拡張、非連続の `8-9` への移動も確認）。
- サーバーGCをCPU `4-7` で実行した場合、4つのヒープスレッドは各1CPUを保持し、バックグラウンドGCスレッドは4つとも `4-7` になることをCoreCLR・Native AOT両方で確認。
- `System.Threading.Thread.Tests`、`System.Threading.ThreadPool.Tests`、`ProcessTests.TestProcessorAffinity` がLinux x64でパス（124件成功、11件スキップ）。
