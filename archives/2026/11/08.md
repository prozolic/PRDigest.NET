- 作成日時: 2026年11月07日 08:54:15(UTC)
- マージ日時: 2026年11月08日 06:53:35(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/community-contribution/index.html"><span style="background-color: #c2e0c6; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">community-contribution</span></a> <a style="text-decoration:none;" href="../../labels/area-NativeAOT-coreclr/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-NativeAOT-coreclr</span></a>
#### 概要
NativeAOT の `ObjectWriter.EmitOrResolveRelocation` が、同一セクション内で定義済みのターゲットに対する arm64 `IMAGE_REL_BASED_ARM64_BRANCH26`（`B`/`BL`）を自前で解決する際、変位が ±128 MB の範囲外でも範囲チェックをしていなかった問題の修正です。

- 修正前：`PutArm64Rel28` は範囲を Debug ビルドの assert でしか検証しないため、リリース版 ILC では変位が 26 ビットにマスクされ、誤ったアドレスへの分岐命令が書き込まれていました。オブジェクトはリンクに成功し、実行時に無関係なコードへ分岐します。
- 修正後：`IMAGE_REL_BASED_THUMB_BRANCH24` と同様に、変位が収まらない場合は自前で解決せずリロケーションを出力します。これによりリンカーが範囲拡張サンクを配置するか、オーバーフローを報告できます。

この問題は、1 つの arm64 コードセクションが 128 MB を超える場合に発生します。作成者によれば、win-arm64（マネージドコードが 1 つの COFF セクションになる）や linux-arm64 の大規模な NativeAOT アプリケーションが該当します。

#### 変更内容
- `src/coreclr/tools/Common/Compiler/ObjectWriter/ObjectWriter.cs`（+2/-1）：`ARM64_BRANCH26` に対して、`THUMB_BRANCH24` と同じ範囲チェックを追加。範囲外の場合はリロケーションを出力する。
- `src/coreclr/tools/Common/Compiler/DependencyAnalysis/Relocation.cs`（+1/-1）：既存の `FitsInArm64Rel28` をオブジェクトライターから参照できるようアクセシビリティを変更。`PutArm64Rel28` 内の Debug assert はそのまま維持。

#### パフォーマンスへの影響
影響なし（記載された情報の範囲では、パフォーマンスに関する変更やベンチマーク結果はありません）。

#### 関連Issue
- [#103073](https://github.com/dotnet/runtime/issues/103073)

#### その他
- 互換性への影響（破壊的変更・非推奨化）は、提供された情報には記載がありません。公開 API の変更はなく、コンパイラツール内部（NativeAOT のオブジェクトライター）の実装修正です。
- テストは追加されていません。範囲外のケースを再現するには 1 セクションに 128 MB 超の arm64 コードが必要で、CI でのコンパイルには大きすぎ時間もかかるためと説明されています。作成者は、大規模な win-arm64 向け NativeAOT アプリケーションのビルドでこの問題を発見し、その環境でこの変更を適用しているとのことです。

- **`src/coreclr/vm/eeconfig.h/.cpp`**: 型名エントリが文字列の所有権を自動管理するようになり、型リストのクリーンアップも自動化。

#### 概要
x64 (Unix / Windows) 向けの EH funclet 呼び出しヘルパー（catch / finally / filter）を CoreCLR と NativeAOT で共有するアセンブリ実装に統合する変更です。他アーキテクチャは別PRで同じテンプレートを使って対応予定とされています。

- 共有ヘルパー `CallEHFunclet`（catch と finally）と `CallEHFilterFunclet` を `src/coreclr/runtime/amd64/EHHelpers.{S,asm}` に追加
- 保存レジスタのロード（NativeAOTでは書き戻しも）はランタイムごとのマクロ（`LOAD_FUNCLET_REGISTER`、`LOAD_FUNCLET_XMM_REGISTER`、`STORE_FUNCLET_REGISTER`）で切り替え
  - CoreCLR: 従来どおり `pRD->pCurrentContext` を渡し、`CONTEXT` から直接ロード（Windowsでは xmm6-xmm15 を含む）
  - NativeAOT: `REGDISPLAY` を渡し、そのレジスタポインタ経由で処理
- NativeAOT 固有の処理は共有ヘルパー内で `FEATURE_NATIVEAOT` により分岐（funclet 呼び出し前後の `TSF_DoNotTriggerGc` のクリア/再設定、funclet 戻り後の `REGDISPLAY` への保存レジスタ書き戻し）
- NativeAOT の catch 後の再開は新設の `RhpResumeAfterCatch` が担当。ExInfo の pop、unhijack、保存レジスタの再ロード（Windowsでは xmm6-xmm15 を含む）、`TSF_DoNotTriggerGc` のクリア、Windowsでの CET シャドウスタックの巻き戻しを行い、再開アドレスへジャンプ。catch funclet 戻りから `RhpResumeAfterCatch` までは `TSF_DoNotTriggerGc` が設定されたままなので、スレッドのハイジャック／サスペンドは発生しない

#### 変更内容
- **共有ヘルパー追加**: `src/coreclr/runtime/amd64/EHHelpers.S` / `EHHelpers.asm`（新規）
- **CoreCLR**
  - `vm/amd64/asmhelpers.S` / `AsmHelpers.asm` から重複していた `CallEHFunclet` / `CallEHFilterFunclet` を削除
  - `vm/amd64/AsmMacros_Shared.{h,inc}` に `CONTEXT` ベースのレジスタロードマクロを追加
  - `vm/eetwain.cpp`: x64 の filter ヘルパーにコンテキスト全体を渡すよう変更
  - `vm/CMakeLists.txt`: 共有 EH アセンブリをビルドに追加
- **NativeAOT**
  - `RhpCallCatchFunclet` / `RhpCallFinallyFunclet` / `RhpCallFilterFunclet` を削除し、`RhpResumeAfterCatch` を追加（`amd64/ExceptionHandling.{S,asm}`）
  - `amd64/AsmMacros_Shared.{h,inc}` に `REGDISPLAY` ベースのロード／書き戻しマクロを追加
  - `StackFrameIterator.cpp`: 新しいヘルパーの認識とハードコードされたフレームレイアウトを更新
  - `Runtime.Base` の `ExceptionHandling.cs` / `InternalCalls.cs`: x64 のディスパッチを共有ヘルパー経由に変更し、ExInfo の明示的クリーンアップを追加
  - `thread.{h,cpp}`: `PopExInfo` を `RhpPopExInfo` として外部から利用可能にした
  - `CMakeLists.txt`、`amd64/AsmMacros.inc`: ビルド入力の更新と未使用の検証ヘルパー宣言の削除
