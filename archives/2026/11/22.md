### [#138093](https://github.com/dotnet/runtime/pull/138093) Pass the custom marshaler managed type to its QCall as a pointer {#138093}
- 作成者: [@lewing](https://github.com/lewing)
- 作成日時: 2026年11月22日 17:12:07(UTC)
- マージ日時: 2026年11月22日 22:00:23(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/arch-wasm/index.html"><span style="background-color: #eb6420; color: #ffffff; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">arch-wasm</span></a> <a style="text-decoration:none;" href="../../labels/area-VM-coreclr/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-VM-coreclr</span></a>
#### 概要
`StubHelpers_CreateCustomMarshaler` QCall が、マネージ型を `TypeHandle` の値渡しで受け取っていたため、Wasm の C ABI では不正なハンドルが読まれていた問題を修正します。マネージ側（`StubHelpers.CreateCustomMarshaler(IntPtr, int, IntPtr)`）は生のハンドルを渡しており、多くのターゲットではポインタ1つのクラスはレジスタ渡しとなるため一致します。しかし Wasm の C ABI では、union をラップするこのクラスが間接渡し（ポインタ経由）になるため、QCall 側がハンドルを「`TypeHandle` へのポインタ」として扱い、型の `MethodTable` フラグやベースサイズをハンドルとして読んでいました。

修正として、他の QCall と同様に `EnregisteredTypeHandle` を受け取るように変更しました（`TypeHandle` を値渡しで受け取る QCall はこれのみでした）。

- browser-wasm: 不正なアドレスが偶然読み取り可能なため、テストは不正なハンドルのまま通過していた
- browser-wasm64（#138027）: アドレスが範囲外となり、`Interop/ICustomMarshaler/ConflictingNames` が `MethodTable::GetInstantiation` でトラップする

#### 変更内容
- `src/coreclr/vm/mlinfo.cpp` (+2/-1): `StubHelpers_CreateCustomMarshaler` の引数を `EnregisteredTypeHandle` で受け取るよう変更
- `src/coreclr/vm/stubhelpers.h` (+1/-1): 対応する宣言の変更

#### パフォーマンスへの影響
影響なし

#### 関連Issue
- [#138027](https://github.com/dotnet/runtime/pull/138027)（このPRはそこから分割されたもの。Issueではなく Pull Request）

#### その他
- 検証: browser-wasm と osx-arm64 のランタイムがビルドできることを確認。browser-wasm64 Checked では、`SameNameDifferentAssembly` と `MultipleALCs` が変更前はクラッシュし、変更後は interpreter と crossgen2 の両方で成功しています。
- 内部実装（VM の QCall シグネチャ）の変更であり、公開APIへの影響や互換性への影響は記載されていません。

### [#137365](https://github.com/dotnet/runtime/pull/137365) \[cDAC\] Fix riscv64/loongarch64 gaps and interpreter stack walking {#137365}
- 作成者: [@am11](https://github.com/am11)
- 作成日時: 2026年11月11日 17:32:03(UTC)
- マージ日時: 2026年11月22日 21:43:10(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/community-contribution/index.html"><span style="background-color: #c2e0c6; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">community-contribution</span></a> <a style="text-decoration:none;" href="../../labels/arch-loongarch64/index.html"><span style="background-color: #eb6420; color: #ffffff; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">arch-loongarch64</span></a> <a style="text-decoration:none;" href="../../labels/arch-riscv/index.html"><span style="background-color: #eb6420; color: #ffffff; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">arch-riscv</span></a> <a style="text-decoration:none;" href="../../labels/area-Diagnostics-cdac/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-Diagnostics-cdac</span></a>
#### 概要
cDAC（診断用データコントラクトリーダー）において、riscv64/loongarch64 を arm64 と同等水準に引き上げ、全アーキテクチャ共通でインタープリター（`DOTNET_Interpreter`）のスタックウォークを修正するPRです。riscv64 実機で cDAC ストレステスト（`DOTNET_CdacStress=0x101`/`0x201`）を実行した際に見つかった問題への対応です。作成者によれば、これにより riscv64 上の全 cDAC ストレスデバギーが JIT／インタープリター両モードで通り、riscv64 ダンプに対する cDAC ダンプテストも通ります。

#### 変更内容
**riscv64 / loongarch64**
- `RISCV64Context` に欠落していた `R0` を追加し、レジスタオフセットを修正（`RISCV64Context.cs`）。これまで全 GPR と `Pc` がネイティブ `CONTEXT` から 8 バイトずれて読まれていた。
- RISC-V/LoongArch64 の FP 構造体分類 `TryGetFpStructInRegistersClassification` を `RuntimeTypeSystem` に実装（`MethodTable::GetFpStructInRegistersInfo` に準拠）。`IRuntimeTypeSystem.cs`、`CdacTypeHandle.cs` も更新し、これまで呼び出し規約で投げていた `NotImplementedException` を解消。
- `InlinedCallFrame` 処理で、最初の引数レジスタ（`A0`）に次の `InterpreterFrame` を設定（`RISCV64FrameHandler.cs`、`LoongArch64FrameHandler.cs`）。
- 両アンワインダーでアンワインド情報の null チェックを追加。
- `ClrDataFrame` に SP レジスタ番号を追加。

**インタープリター（全アーキテクチャ）**
- インタープリター用 GC 情報エンコーディングでデコードし、フレーム相対スロットを扱い、アクティブなコールイーのフレーム内スロットをスキップ（`StackWalk_1.cs`、`GcScanner.cs`）。
- `InterpreterFrame` の continuation を報告（`Continuation` データ記述子フィールドを新設。`datadescriptor.inc`、`frames.h`、`InterpreterFrame.cs`）。
- インタープリターのファンクレット（EH 句のハンドラー／フィルター範囲）を認識（`ExecutionManagerCore.cs`）し、`VirtualUnwindInterpreterCallFrame` と同様に呼び出し元コンテキストを計算（`FrameHelpers.cs`、`StackWalk_1.ExceptionHandling.cs`）。これによりランタイム同様、ファンクレットの親やアンワインド済みフレームがスキップされる。

**ドキュメント／テスト**
- `RuntimeTypeSystem.md`、`StackWalk.md`、`data-descriptor-meanings.json` を更新。
- `FpStructClassificationTests.cs`、`PlatformContextTests.cs`、`StackWalkTests.cs`、MockDescriptors を追加／更新。

#### パフォーマンスへの影響
影響なし（診断用 cDAC の正確性修正であり、ベンチマーク結果の記載もありません）。

#### 関連Issue
なし

#### その他
- 依存PR: [microsoft/clrmd#1527](https://github.com/microsoft/clrmd/pull/1527)（riscv64/loongarch64 のダンプテスト用）、[dotnet/runtime#137337](https://github.com/dotnet/runtime/pull/137337)（riscv64/loongarch64 のインタープリター用）。

  - **Medium**: FP 構造体分類および呼び出し規約に対する、焦点を絞った回帰テストが不足している。
  - **Medium**: インタープリターのスロット解決とコールイーのフィルタリングに対するテストが不足している。
