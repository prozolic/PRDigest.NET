### [#137033](https://github.com/dotnet/runtime/pull/137033) JIT: don't CSE the source load of an in-place memory update on xarch {#137033}
- 作成者: [@lewing](https://github.com/lewing)
- 作成日時: 2026年11月05日 17:32:06(UTC)
- マージ日時: 2026年11月07日 00:52:30(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-CodeGen-coreclr/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-CodeGen-coreclr</span></a>
#### 概要
xarch（x86/x64）向けJITの共通部分式削除（CSE）において、`*p = *p op x` 形式のインプレースなメモリ更新でソース側のロードがCSE対象になるのを防ぐ変更です。ロード値がレジスタに保持されるとLoweringが `op [mem], x` 形式（RMW）を生成できなくなるため、CSE候補選択後にそのような候補を後段でスクリーニングして除外します。#136612から分割され、CSE側のスクリーニングのみを単独で導入します。

変更後のコード生成例（`int old = holder.Flags; holder.Flags |= 0x40; return old;`）:

```diff
        mov      eax, dword ptr [rcx+0x10]
-       mov      edx, eax
-       or       eax, 64
-       mov      dword ptr [rcx+0x10], eax
-       mov      eax, edx
+       or       dword ptr [rcx+0x10], 64
```

#### 変更内容
- `src/coreclr/jit/compiler.h`（+3）: `TARGET_XARCH` 限定の新規メソッド宣言
- `src/coreclr/jit/optcse.cpp`（+134）: `optValnumCSE_Locate` に後段スクリーニング `optValnumCSE_ScreenMemoryUpdates` を追加（`TARGET_XARCH` のみ）
  - `STOREIND(addr, op(IND(addr), x))` の形で、`op` がRMWメモリオペランド形式を持つ場合（`OperIsRMWMemOp`、または `NOT`/`NEG`）、ロードのCSE出現を解除します。ロードは op1 であること（`op` が可換なら不問）、アドレスはLoweringと同様に `GenTree::Compare` で照合します。当該候補の残りの出現は引き続きCSE可能です。
  - `op` 自体が他の出現を持つCSE候補である場合は、`op` の結果に他の使用があるためロードを維持します。ロードを除外すると別のロードの `op` の唯一の他出現が消える場合があるため（`*p &= a; *p |= b;`）、固定点に達するまで反復します。
  - `optValnumCSE_InitDataFlow` は解除済みの出現をスキップします（後続フェーズは既に `IS_CSE_INDEX` を確認済み）。
- `src/tests/JIT/opt/CSE/InPlaceMemoryUpdate.cs` / `.csproj`（新規）: `or`/`add`/可換な`or`（フィールド）、`and`/`not`/`neg`（ref経由）をカバーするdisasmテスト

#### パフォーマンスへの影響
ローカルのSuperPMI asmdiffs（windows x64、Checked JIT、baseは main 5c994824781）の結果:

| コレクション | コンテキスト数 | 差分のあるメソッド | 小さく/大きく | サイズ | PerfScore（改善/悪化メソッド） |
|---|--:|--:|--:|--:|--:|
| benchmarks.run | 46,242 | 316 | 291 / 24 | -1,795 B (-0.009%) | +0.015% (19 / 294) |
| benchmarks.run_pgo | 86,655 | 400 | 395 / 1 | -2,305 B (-0.007%) | +0.018% (25 / 346) |
| aspnet2.run | 16,927 | 10 | 10 / 0 | -76 B (-0.004%) | +0.002% (3 / 7) |

- コードサイズはほぼ全般で減少します。一方、PerfScoreはメモリオペランド形式をload/op/storeより遅く評価するため増加します（値が既にレジスタにある場合でも `inc dword ptr [mem]` のスコアが高くなります）。
- 悪化例（PerfScoreのみ）: `Perf_Regex_Industry_SliceSlice:Count`（run_pgo, Tier1-OSR, -4 B, +16,404）。ホットブロックでフィールド比較後にインクリメントする箇所で、CSEされなくなりました。`RegexInterpreter:Scan`、`Regex:RunAllMatchesWithCallback`、`SciMark2.kernel:RandomMatrix` も同様の形状です。`StackTrace:ToString`（-60 B, +114）では `StringBuilder.Append(char)` のインライン化箇所が `inc dword ptr [rbx+0x18]` になります。
- 改善例: `FrozenHashTable:CalcNumBuckets`（-63 B, -56）はレジスタ圧力の低下でスピルが減り、フレームが16バイト縮小します。`Benchstone.BenchI.Pi:ComputePi`（-21 B）は `push rdi`/`push rsi` が不要になります（ただしPerfScoreは+25）。
- aspnetのカバレッジは約41%に留まります（41,203件中23,709件がmiss、567件がエラー、baseとdiffで同一）。
- 参考: #136612（VNストア転送あり）上に同変更を適用した場合、libraries.pmiは -17,809 B（PerfScore +0.015%）、libraries.crossgen2は -2,877 B（PerfScore +0.005%）でした。

#### 概要
JITの最適化（`optimizebools.cpp`）において、比較チェーン（compare chain）を形成する際に、結合後のブロックが引き継ぐブロックウェイト（実行頻度の推定値）を修正するPRです。
チェーン形成では最初のブロックの条件が2番目のブロックへ移され、2つのブロックが圧縮（compaction）されます。従来は結合後のブロックが2番目のブロックのウェイトを持っていましたが、2番目のブロックの唯一の先行ブロックは最初のブロックであり、両者間のエッジは無条件になります。そのため結合後のブロックは最初のブロックと同じ頻度で実行されるはずであり、最初のブロックのウェイトを継承するように変更されました。

#### 変更内容
- `src/coreclr/jit/optimizebools.cpp` (+4/-8): 比較チェーン形成時のブロックウェイトの扱いを修正し、結合ブロックが最初のブロックのウェイトを継承するようにした。

#### パフォーマンスへの影響
生成コードのウェイト情報（PGO/ブロック頻度の整合性）に関する修正です。
作成者によると、#136994 で見られたperfスコアの回帰（偽陽性）の原因が、fold処理が最初のブロックのウェイトを保持する一方、main上のチェーン処理は2番目のウェイトしか保持していなかった点にあったとのことです。この修正によりその不整合が解消される見込みです。
ベンチマーク結果などの具体的な数値は提供されていません。

- **PAL 実装の削除**: `pal/src/file`（`file.cpp`、`directory.cpp`、`path.cpp`）と `pal/src/map`、関連ヘッダ（`file.h`、`file.hpp`、`map.hpp`）、PAL テスト群（file_io、filemapping_memmgt、関連テストの登録）を削除。`pal.h` / `palprivate.h` から対応する宣言も削除。
- **呼び出し元の移行（Unix）**:
  - メタデータ `StgIO`（`md/enc/stgio.cpp`、`stgio.h`）: `FILE*` と `VMToOSInterface` によるマッピングへ変更。
  - メモリマップ式 stress log（`utilcode/stresslog.cpp`）: stdio / `ftruncate` / `mmap` を使用。
  - デバッガー/診断トランスポート名（`pal/src/thread/process.cpp`）と createdump の既定ダンプパス: `TMPDIR` を直接参照。createdump では末尾の `/` が欠けていた点を補うよう変更。
- **PAL オブジェクト型の整理**: `corunix.hpp` で PAL オブジェクト型をスレッドのみに縮小。1 箇所でしか使われない PAL ヘルパー（`StringHolder` など）は呼び出し元へ統合または削除。
- **Windows 専用化**: `SearchPathWrapper`、`GetFileSize` ラッパー、Win32 マップビューホルダー（`holder.h`）などを Windows 限定に。
- **GC**: `gcenv.unix.cpp` のアドレス空間関連チェックを `RLIMIT_AS` ベースに変更。
- **ビルド設定**: 利用者がなくなった configure チェック（`HAVE_PROCFS_STATM`、`ONE_SHARED_MAPPING_PER_FILEREGION_PER_PROCESS`、`REALPATH_SUPPORTS_NONEXISTENT_FILES`、`OPEN64_IS_USED_INSTEAD_OF_OPEN`、`WRITE_0_BYTES_HANGS_TTY`）と、`tryrun*.cmake` 内の対応するキャッシュ値を削除。`mscordac_unixexports.src` からも該当エクスポートを削除。

規模としては `file.cpp`（約 2,500 行削除）、`path.cpp`（約 760 行）、`directory.cpp`（約 570 行）が大きく、その他 PAL テスト群が多数削除されています。

#### パフォーマンスへの影響
影響なし（提供情報にベンチマーク結果や性能に関する記述はありません）。Unix 側のファイル/マッピング処理は PAL 経由から直接の stdio/POSIX 呼び出しに変わりますが、性能への影響は提供情報からは確認できません。
