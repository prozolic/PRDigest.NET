### [#137082](https://github.com/dotnet/runtime/pull/137082) \[mono\] Fix SizeConst array marshalling overflows {#137082}
- 作成者: [@BrzVlad](https://github.com/BrzVlad)

#### 概要
Mono ランタイムにおいて、`[MarshalAs(UnmanagedType.ByValArray, SizeConst = N)]` を持つ構造体を `Marshal.StructureToPtr` でマーシャリングする際、配列の要素数が `SizeConst` と一致しない場合に発生していたバッファオーバーフローを修正します。

- blittable 型の場合: 配列が `SizeConst` より小さいと、配列が保持するバイト数を超えてコピーしていました（読み取りオーバーフロー）。
- 非 blittable 型の場合: 配列が `SizeConst` より大きいと、コピー先バッファを超えて書き込んでいました（書き込みオーバーフロー）。

修正後は、配列の要素数が不足している場合に実行時例外をスローし、コピー量を `SizeConst` に制限することで、読み取り・書き込みの両方のオーバーフローを防ぎます。

```csharp
[StructLayout(LayoutKind.Sequential)]
internal struct MyStruct
{
    [MarshalAs(UnmanagedType.ByValArray, SizeConst = 20)]
    public int[] Values;
}
// Marshal.StructureToPtr(str, buffer, false);
```

#### 変更内容
- `src/mono/mono/metadata/marshal-shared.c` (+10/-2): ByValArray マーシャリング処理で、配列要素数のチェックと `SizeConst` 上限でのコピー制限を追加。
- `src/libraries/System.Runtime.InteropServices/tests/.../Marshal/StructureToPtrTests.cs` (+0/-2): テストの変更（2行削除。詳細は提供情報からは不明）。

#### パフォーマンスへの影響
影響なし（ベンチマーク結果の記載なし）。

#### 関連Issue
なし

#### その他
- 修正対象は Mono ランタイム固有の実装（ネイティブ側 C コード）で、公開 API の変更はありません。
- メモリ安全性に関わる修正ですが、CVE 番号などの記載は提供情報にはありません。
- 配列が `SizeConst` より小さい場合に例外がスローされるようになるため、従来この状況で（未定義動作のまま）動作していたコードは挙動が変わる可能性があります。

#### 概要
`[MarshalAs(UnmanagedType.LPUTF8Str)] StringBuilder` と `[MarshalAs(UnmanagedType.LPWStr)] StringBuilder` 用のIL stubが、ネイティブバッファのサイズ計算をオーバーフロー検査なしのint32演算で行っていた問題を修正します。`StubHelpers.CheckStringLength` は `StringBuilder.Capacity` を `0x7ffffff0` までしか制限しないため、大きな Capacity ではサイズ計算が桁あふれ（ラップ）していました。

- **UTF-16** (`ILWSTRBufferMarshaler`): `Capacity * 2 + 4`。約1G文字以上になると、追加のnull終端のオフセットが負になり、確保したバッファの約2GB手前に書き込みます。

両者とも、`ILCSTRBufferMarshaler` が既に行っているのと同様に `MUL_OVF`/`ADD_OVF` を使うよう変更され、メモリ確保や書き込みの前に `OverflowException` がスローされます。by-value、by-ref、フィールドの各ケースはこのサイズ計算を共有しており、native-to-managed方向にはサイズ計算がありません。

#### 変更内容
- `src/coreclr/vm/ilmarshalers.cpp`（+9/-6）: UTF-8とUTF-16のバッファサイズ計算を、オーバーフロー検査付きの `MUL_OVF`/`ADD_OVF` に変更
- `src/tests/Interop/StringMarshalling/LPTSTR/LPTSTRTest.cs`（+25/-0）: `LPTStrTest.StringBuilderNativeBufferSizeOverflow` を追加
- `src/tests/Interop/StringMarshalling/UTF8/UTF8Test.cs`（+28/-0）: `UTF8Test.StringBuilderNativeBufferSizeOverflow` を追加

テストは、問題を引き起こす最小の Capacity（715,827,883 と 1,073,741,823）の StringBuilder を渡し、`OverflowException` を検証します。
- StringBuilderに1.4〜2GBの仮想メモリが必要なため、64ビットCoreCLRに限定し、StringBuilderを確保できない場合は早期にreturnします。
- 周辺のテストと同様に OuterLoop です。

osx-arm64 Releaseでの結果:
- 修正なし: 両テストともマーシャリングstub内で `AccessViolationException` が発生してプロセスがクラッシュ
- 修正あり: 両テストとも成功

影響なし（提供された情報にベンチマークの記載はありません）。なお、サイズ計算がオーバーフロー検査付き演算になりますが、これについて性能面の言及は提供情報にはありません。
