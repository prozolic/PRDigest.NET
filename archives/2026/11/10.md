### [#136897](https://github.com/dotnet/runtime/pull/136897) \[browser\]\[coreCLR\] corerun: exit Node naturally after main returns {#136897}
- 作成者: [@lewing](https://github.com/lewing)
- 作成日時: 2026年11月03日 06:11:07(UTC)
- マージ日時: 2026年11月10日 01:28:44(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-VM-coreclr/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-VM-coreclr</span></a>
#### 概要
`corerun.js`（browser/WebAssembly 向け CoreCLR ホスト）が Node 上で `process.exit()` を呼ぶことで発生する、Node/V8 のシャットダウン時デッドロック（nodejs/node#64274）を回避する修正です。`JIT/jit64/regress/vsw/539509/test1_539509` が `Passed.` 出力後に node が終了せずタイムアウトする問題（R2R-CG2 browser wasm Checked レッグ）に対処します。

原因は、`_proc_exit` オーバーライド（#132078）が `process.exit()` を呼ぶと V8 のプラットフォームワーカースレッドを join するものの isolate を dispose しないことです。バックグラウンドのコンパイルジョブが `CollectionBarrier::AwaitCollectionBackground` で、メインスレッドしか実行できない GC を待っていると、join が戻りません。上流の修正（nodejs/node#66171）は未マージのため、Helix イメージの node v24.22.2 が影響を受けます。

#### 変更内容
- `src/coreclr/hosts/corerun/wasm/libCorerun.js`（+27/-1）
  - **Node 上でのハード終了の限定**: `process.exit()` を使うのは、wasm 内部から終了が要求された場合（JS スタック上に wasm フレームがある場合、例: `Environment.Exit`）のみです。この場合は `ExitStatus` を生きた CLR フレームを通して unwind させてはいけない（#131937）ため、従来どおり即時終了します。
  - **自然終了への切り替え**: それ以外（main が return 済み、またはタイマー tick 完了後）は Emscripten 本来の `_proc_exit` に処理を委ねます。`process.exitCode` を設定し、イベントループが空になった時点で Node が終了するため、isolate が dispose され、待機中のワーカーも解放されます。
  - **遅延 `_exit` の無視**: ランタイム終了後に `SystemJS_ResolveMainPromise` が corerun 向けにキューイングする `_exit` を無視します。従来は `process.exit()` が先にプロセスを終了させるため実行されませんでしたが、ガードがないと終了コード 0 で Emscripten の `exitRuntime` アサーションに抵触します。

#### パフォーマンスへの影響
実行速度への影響はほぼありません。ストレスなしの平均実行時間は 656 ms 対 652 ms（修正後 vs 現行）で、同等です。

シャットダウンのハング頻度は次のとおりです。
- 再現: 約 1,000〜2,000 回に 1 回、`Passed.` 後にハングします。
- `--stress-concurrent-allocation` 下では、現行ホストで 60 回中 3 回のハング、修正後は 180 回中 0 回でした。

- 参照: [#132078](https://github.com/dotnet/runtime/issues/132078)（`_proc_exit` オーバーライド導入）、[#131937](https://github.com/dotnet/runtime/issues/131937)（wasm フレームを通した `ExitStatus` unwind の問題）
- 参照（別リポジトリ）: nodejs/node#64274（デッドロックの原因）、nodejs/node#66171（上流の修正、未マージ）

#### その他
- 動作の同一性は、終了コード・出力の比較で確認されています。対象は return 0、return 100、`Environment.Exit(42)`、`Environment.Exit(0)`、async Main の 3/0 返却、未処理例外、ファイナライザ付き GC です。

#### 概要
`Dictionary<TKey, TValue>.Clear()` において、`Entry` がマネージド参照を含まない場合（キー・値とも参照を含まない場合）、エントリ配列のクリア（`Array.Clear(_entries, ...)`）をスキップする最適化です。`List<T>.Clear()` と同様のパターンで、`RuntimeHelpers.IsReferenceOrContainsReferences<Entry>()` が false のときのみ配列クリアを省略します。

作成者によれば、65,536 エントリの `Clear()` 平均時間が `int` 値で 78.6%、64 バイトの値型で 96.5% 短縮されたとのことです。

#### 変更内容
- `src/libraries/System.Private.CoreLib/src/System/Collections/Generic/Dictionary.cs`（+6/-1）
  - `Clear()` 内のエントリ配列クリアを `RuntimeHelpers.IsReferenceOrContainsReferences<Entry>()` の条件下に限定。
  - バケット配列のクリアとカウンタのリセットは従来どおり無条件で実行（これにより古いエントリは到達不能になる）。
  - 再利用の安全性についての説明コメントを追加。
- `src/libraries/System.Collections/tests/Generic/Dictionary/Dictionary.Generic.Tests.cs`（+45/-0）
  - `Clear_AfterRemovingEntries_CanRefill` テストを追加（要素削除 → `Clear()` → 再充填、`CollectionsMarshal.GetValueRefOrAddDefault` が default を返すことの検証を含む）。
  - `System.Runtime.InteropServices` の using を追加。

**技術的ポイント**
- 影響範囲は公開 API の内部実装（BCL `Dictionary`）で、公開 API の変更はなく、互換性への影響（破壊的変更）の記載はありません。
- 作成者の説明では、各挿入処理がエントリの全フィールドを初期化してから再利用するため、参照を含まない `Entry` では配列クリアを省略しても安全とされています。
- 参照を含む `Entry` では従来どおりクリアが維持されます（GC による解放のため）。
- 作成者は、最適化済み x64 コードにおいて JIT が条件を畳み込み、参照なしエントリでは条件分岐とクリア処理が除去されることを確認したと述べています。

#### 概要
命令レベルのGCストレス（`DOTNET_GCStress`）が、これまでJITコンパイル済みコードのみを計測対象とし、ReadyToRun（R2R）メソッドをスキップしていた問題に対応するPRです。R2Rエントリポイント（asyncの再開スタブを含む）の公開前にGCカバレッジの計測を行い、R2Rコードでもストレステストが可能になります。

#### 変更内容
- **計測処理（readytoruninfo.cpp / prestub.cpp / method.cpp / method.hpp）**: R2Rエントリポイント公開前に `SetupGcCoverage` を呼び出し、asyncの再開スタブも対象にしています。セットアップは直列化され、共有ジェネリックコードでは正規化されたメソッドID（canonical method identity）とデフォルトのコードバージョンを使用します。Apple プラットフォームは除外されています。
- **パッチ処理（gccover.cpp / gccover.h / threadsuspend.cpp / codeman.cpp）**: 計測と命令復元の両方でイメージ上への書き込みをサポートします。JITコードでは従来のexecutable-allocatorのマッピングを維持します。x86では受け手（receiver）を考慮した呼び出し先解決が追加されています。
- **jitinterface.cpp**: R2Rコードを対応するデフォルトのネイティブコードバージョンに関連付けます。
- **ドキュメント（investigate-stress.md）**: Apple プラットフォームでのイメージパッチの制限を明記しています。
- **テスト**: 通常メソッドと共有ジェネリックのR2Rメソッドで、GCの発生とライブ参照の保持を検証する回帰テストが追加される旨が記載されています（変更ファイル一覧には含まれていません）。

#### パフォーマンスへの影響
通常の実行パフォーマンスに関する記載はありません。GCストレス有効時（診断用途）のR2Rコードの計測に関する変更であり、ベンチマーク結果は提供されていません。
