### [#134672](https://github.com/dotnet/runtime/pull/134672) Allow whitespace after leading numeric signs and parentheses {#134672}
- 作成者: [@tannergooding](https://github.com/tannergooding)

#### 概要
`NumberStyles.AllowLeadingWhite`が設定されているときに、先頭の符号または開き括弧の直後のホワイトスペースを許可する機能を実装しました。これにより、末尾のホワイトスペース処理と一貫性を持たせています。整数パースは高速パスを維持しながら、符号後のホワイトスペースには共有パーサーを使用し、16進浮動小数点パース処理も調整しています。

```csharp
// 例：AllowLeadingWhiteが設定されている場合
int.Parse("  +  123", NumberStyles.AllowLeadingWhite); // 許可
int.Parse("  (  123", NumberStyles.AllowLeadingWhite); // 許可
```

#### 変更内容
- **src/libraries/Common/src/System/Number.Parsing.Common.cs**: 共有数値パーサーの符号/括弧後のホワイトスペース処理を更新（+3/-3）
- **src/libraries/System.Private.CoreLib/src/System/Globalization/NumberStyles.cs**: `AllowLeadingWhite`のドキュメント更新（+3/-3）
- **src/libraries/System.Private.CoreLib/src/System/Number.Parsing.cs**: 整数パース最適化と符号後のホワイトスペース処理追加（+15/-0）
- **テストファイル**: Int32、Double、Decimal、BigIntegerの回帰テストを追加（計56行追加）
  - 数値型、カスタム符号、括弧、UTF-8、部分パース時の消費長に関するカバレッジを強化

#### パフォーマンスへの影響
一般的なケースでのJIT回帰は確認されていません。ReadyToRunで`int.Parse`に先頭ホワイトスペースがある場合、修正前5.9nsから修正後6.4nsへの計測差異がありますが、JIT専用実行では再現せず、コードレイアウトに依存する可能性があります。ベンチマークツール（BenchmarkDotNet）は.NET 11ランタイムで認識不可。

#### 関連Issue
[#101873](https://github.com/dotnet/runtime/issues/101873)

#### その他
- テスト実績：System.Runtime数値型テスト36,311件（失敗0件、スキップ71件）、System.Runtime.Numericsテスト8,635件（失敗0件）
- 修正前では11件のInt32回帰テストケースが失敗し、修正後に合格
- `AllowLeadingWhite`を設定しない場合、該当入力は従来通り無効

スレッドプール環境での典型的なサーバーワークロード（複数の異なるリクエストをスレッド再利用で処理）では、バースト内での同一値の繰り返しに対して効果的です。

- Copilotレビューコメント: スレッドローカルフィールドの配置が他のフィールド宣言より後ろにあるため、レポジトリのコーディング規約に従いフィールドセクションに移動することが推奨されています

### [#133304](https://github.com/dotnet/runtime/pull/133304) Implicit byref arguments are never on the GC heap {#133304}
- 作成者: [@EgorBo](https://github.com/EgorBo)
- 作成日時: 2026年09月05日 14:23:17(UTC)
- マージ日時: 2026年09月25日 09:04:43(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/area-CodeGen-coreclr/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-CodeGen-coreclr</span></a>
#### 概要
インプリシット byref 引数（暗黙的に参照渡しされるスタラクト）が確実に GC ヒープ上に存在しないことを保証する変更です。これにより、呼ばれた側がこれらのスタラクトへの書き込みに際してライトバリア（write barrier）の発行をスキップでき、生成されるコード量と実行コストが削減されます。

例えば、16バイトの S16 スタラクトに対する書き込みは、ライトバリア呼び出しなしの直接メモリ書き込みになり、コードサイズが32バイトから19バイトへ削減されます。

```csharp
struct S16 { public object A; public object B; }

[MethodImpl(MethodImplOptions.NoInlining)]
static void Store(S16 s, object o) { s.A = o; Sink(ref s); }
```

#### 変更内容
- **JIT コンパイラ**: インプリシット byref 引数をヒープ外ストレージとしてマーク（`morph.cpp`、`lclvars.cpp`、`promotion.cpp`）し、ライトバリア不要の最適化を有効化
- **ABI ドキュメント**: インプリシット byref ストレージの不変式を明記（`clr-abi.md`）
- **ReadyToRun バージョン**: メジャーバージョン 30 へ昇格（`readytorun.h`、`ModuleHeaders.cs`、`ModuleHeaders.h`）。crossgen2 が今後バリア省略コードを生成するため、旧ランタイムは新しいイメージを拒否する必要があります
- **デバッガ func-eval**: 引数を GC 保護されたネイティブメモリへコピー（`funceval.cpp`）
- **ランタイムアサーション**: 呼び出し側でインプリシット byref 引数がヒープ上でないことを検証（`callhelpers.cpp`、`callhelpers.h`）

#### パフォーマンスへの影響
**改善あり**
- ライトバリア呼び出しの削減により、コードサイズ削減（実例: 32 → 19バイト）
- メモリ書き込みの高速化（`CORINFO_HELP_CHECKED_ASSIGN_REF` 呼び出し廃止）
- スタック操作（`push`/`pop`）の最適化

#### 関連Issue
[#133961](https://github.com/dotnet/runtime/issues/133961)

#### その他
- **互換性**: `MINIMUM_READYTORUN_MAJOR_VERSION` は 26 のまま。既存イメージが暗黙的 byref を転送する場合は引き続きサポート
- **注記**: Copilot レビューで、アーキテクチャドキュメント（WebAssembly など）や自動リグレッション テストの強化が提案されています

### [#132721](https://github.com/dotnet/runtime/pull/132721) Interpreter block-count PGO for WebAssembly CoreCLR {#132721}
- 作成者: [@pavelsavara](https://github.com/pavelsavara)
- 作成日時: 2026年08月24日 22:35:28(UTC)
- マージ日時: 2026年09月25日 06:36:10(UTC)
- ラベル: <a style="text-decoration:none;" href="../../labels/arch-wasm/index.html"><span style="background-color: #eb6420; color: #ffffff; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">arch-wasm</span></a> <a style="text-decoration:none;" href="../../labels/area-VM-coreclr/index.html"><span style="background-color: #d4c5f9; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">area-VM-coreclr</span></a> <a style="text-decoration:none;" href="../../labels/os-browser/index.html"><span style="background-color: #FEF2C0; color: #000000; display: inline-block; padding: 0 7px; font-size:12px; font-weight:500; line-height:18px; border-radius:2em; border:1px solid transparent;">os-browser</span></a>
#### 概要

WebAssemly上のCoreClRインタープリタに対して、ブロックカウントPGO（Profile-Guided Optimization）インストルメンテーションを追加し、EventPipe経由でプロファイルデータを収集できるようにする変更です。シングルスレッドのブラウザ/WASI環境向けで、`dotnet-pgo`がR2Rプリコンパイル用の`.mibc`ファイルを生成できるようになります。マルチスレッドWASMではこの機能はコンパイルアウトされます。

#### 変更内容

**インタープリタ側の変更：**
- 新しい`INTOP_PGO_COUNT`インタープリタオペコードを追加（シングルスレッドのみ）し、ネイティブ`uint32_t`カウンタをインクリメント
- `InterpCompiler::InstrumentBlockCounts`で**ブロック先頭のみ**に`BasicBlockIntCount`プローブを挿入（メソッドエントリと分岐/スイッチ/ループターゲット）
- `DOTNET_InterpPgo`環境変数でゲート、`DOTNET_InterpPgoMethods`で対象メソッド フィルタリング可能

**EventPipe側の変更：**
- EventPipeセッション停止時に`JitInstrumentationDataVerbose`イベントとして蓄積カウントを出力
- 新しい`ep_rt_session_stopping`フックを導入し、セッション停止時にPGOデータを`PgoManager::EmitInstrumentationDataToEventPipe()`で自動フラッシュ
- テキストファイルエクスポート（`DOTNET_WritePGOData`）はシャットダウンパスに限定

**JavaScript診断クライアント側の変更：**
- `collectPgoTrace()` 関数（`js://pgo`）でトレース開始と10秒後の自動`.nettrace`ダウンロード
- プロセスごとにワンショット実行（インタープリタカウンタは累積的なため、複数回実行すると重複データとなる）

**共有PGO インターフェース：**
- JITとインタープリタが共有するPGO割り当てメソッドを`CEECodeGenInfo`基底クラスに移行
- ブラウザ/WASI向けにティアリングゲートを緩和

#### パフォーマンスへの影響

影響なし。本変更はプロファイルデータ収集に限定されており、ランタイム性能への直接的な低下は確認されていません。ただし、以下の懸念が指摘されています：

- **マルチスレッドビルドでの競合状態：** `INTOP_PGO_COUNT`がマルチスレッド環境で実行される可能性があり、複数ワーカーがカウンタにレースする恐れがあります（符号付き整数のオーバーフロー対応が必要）
- インタープリタのティアリングゲート緩和により、JITのPGO段階でも非ティアリング対象メソッドの計測が可能になる点
